# 任务 U1：大的归档分片上传

2026-10-03 用户反馈：上传 ChatGPT 导出文件一直提示「网络连接中断，读取这个文件没有完成」。由协调者直接实现。

## 原因

线上站点前面是 Cloudflare，它对单个请求的大小有上限（常见是 100 MB），超过的请求在到达服务器之前就被断开。服务器日志里没有这次上传的任何记录，页面只能看到连接断了。另外原来的做法是读取时传一遍、确认导入时再传一遍，同一个文件要完整上传两次。

## 规则

- 文件超过 32 MB 时，页面把它切成 8 MB 一片依次上传；32 MB 以内的照旧一次传完。
- 一片没传成（连接断了、服务器忙）会等一下重传这一片，最多连续失败 5 次才报错；服务器会告诉页面已经收到多少，从那里接着传。
- 读取（预览）和确认导入用的是服务器上已经收好的同一份，文件只上传一次。
- 服务器上的分片是临时文件：导入开始后删掉；两小时没动的删掉；同一个人最多同时留 3 份，再多就删最早的。服务重启后这些临时文件不保留，页面发现后会自动重传一次。
- 文件大小上限不变（200 MB，由 `connectors.MaxUploadBytes` 决定），超过时在开始上传前就提示太大。
- 只有主人能上传、读取、丢弃。

## 接口

- `POST /v1/connectors/archive/uploads`，`{ "name", "size" }` → `201 { "id", "pieceBytes" }`；太大返回 `413 archive_too_large`。
- `PUT /v1/connectors/archive/uploads/{id}?offset=N`，请求体是这一片的内容 → `{ "received" }`；`offset` 不等于已收到的长度时返回 `409 { "error": "upload_offset", "received" }`。
- `DELETE /v1/connectors/archive/uploads/{id}`。
- `POST /v1/connectors/archive/preview` 和 `POST /v1/connectors/archive` 除了原来的表单上传，也接受 JSON：`{ "upload": "<id>", "organize": "later|now" }`。

## 测试

- `internal/httpapi/archive_uploads_test.go`：按顺序收片、重复的片不重写、没收全不能读、超出声明大小的片被拒绝且不留在文件里、读取和导入拿到的内容和原文件一字节不差、导入后分片删除、不是主人不行。
- `web/tests/phase2-batch4.spec.ts` 最后一条：40 MB 的文件切成 5 片，第三片掉线一次后续传，读取和导入之间不重传。

## 补充（同一天）：压缩包只上传里面的对话文件

分片上线后用户的导出文件仍然传不了：它超过了 200 MB 的上限，页面提示「文件超过可读取的大小，请拆成几份后再导入」。这个上限是按「整个压缩包」算的，而 ChatGPT 的导出里绝大部分是图片和语音，真正要导入的对话文件只占很小一部分。让用户自己拆压缩包不合理。

改成：

- 选了 zip 之后，浏览器先读压缩包末尾的目录，找到 `conversations.json`，只把这一个文件取出来上传。整个压缩包不会被读进内存，也不上传，所以压缩包多大都可以（包括超过 4 GB 的）。实现在 `web/src/domain/zipSlim.ts`，不依赖第三方库。
- 取出来的对话文件照常走上面的规则：32 MB 以内一次传，超过就分片。
- 压缩包里没有 `conversations.json`、加了密、或者用了浏览器解不了的压缩方式时，按原来的办法整个上传，由服务器处理。
- 上限改成按对话文件算，并从 200 MB 提到 512 MB（`connectors.MaxUploadBytes`，和解开后的上限 `MaxArchiveBytes` 一样）。
- 页面上显示的名字仍然是用户选的那个压缩包的名字。

**图片和语音不上传、不解析**（2026-10-03 用户让协调者决定）。理由：记忆只从用户自己说的话里整理，图片里的内容几乎都在前后文字里谈到了；解析每张图要调一次看图的模型，花费和时间都高；原图要占服务器磁盘，而这台机器只剩约 7 GB。对话里「这条消息带了图片」的标记还在。以后要做的话放到第 5 阶段多模态接入里，按需对单条消息解析，已记入待办清单。

测试：`web/tests/phase2-batch4.spec.ts` 最后一条（45 MB 的压缩包，带语音和图片，实际上传的只有对话文件，文件名和内容都核对）；另用真实压缩工具写出的普通、zip64、不压缩、没有对话文件四种压缩包手工核对过取出的内容一字节不差。

## 再次修复：浏览器的 ZIP 解压兼容

用户反馈 `gpt20261004.zip`（1250 MB）仍提示超过可读取大小。公网构建在浏览器没有 `DecompressionStream`、或该接口不支持 ZIP 使用的 `deflate-raw` 时，会退回整包上传，进而触发 512 MB 上限。使用有效的 1250 MB ZIP 已复现这两种失败条件；未拿到用户原始文件，不能据此断定其浏览器的具体情况。

`zipSlim.ts` 加入固定版本的 `fflate` 流式 DEFLATE 后备：原生解压不可用或失败时，继续只读取并解压目录指向的对话文件，不读取媒体。逐块保留独立输出缓冲区，检查解压长度与 ZIP 声明一致。原有 ZIP64 定位、分片上传、预览和导入流程保持适用。

回归测试在磁盘上生成有效的 1250 MB 稀疏 ZIP，包含媒体和跨多个输入块的压缩对话；分别模拟原生支持、完全没有原生接口、原生接口不支持 raw DEFLATE。三种情况下均验证预览和导入只发送原样的对话 JSON，不创建整包上传。原生接口缺失和格式不支持两项在修复前失败。
