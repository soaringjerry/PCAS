## 为什么验收没有拦住

1. **只在实验室里验收。** E 的自动化用例用 httptest 假模型；真实模型走查用的是 API 通道（`openai-api`），工作区时区是上海，Telegram 和推送用的是假服务。用户实际使用的是 ChatGPT 订阅（Codex）通道、墨尔本时区、真实的 Telegram，**这套配置在部署前一次都没有测过。**
2. **地基里的假设没有被审视。** 拆任务时只看了要改的模块，没有检查秘书依赖的适配层（Codex 指令），也没有检查环境默认值（时区）。
3. **规则本身留下了吞错误的空间。** B1 和 C1 的任务文档里写的就是「失败统一回退」「失败统一返回 400」，执行者照做了。
4. **部署后只检查了健康状态。** `/healthz` 正常、首页能打开就当作部署完成，没有真的对秘书说一句话。

## 改进（已写入规则）

- [设计原则](../design/principles.md)新增「出错要说清楚」：每个失败都要给出具体原因和处理办法，同时留一条不含正文和密钥的日志。
- [第 1 阶段共同规则](../tasks/phase1/README.md)新增：
  - 真实模型验收必须走用户的默认通道；
  - 每次部署后，必须在线上用默认通道做冒烟测试：一个问题、一句带时间的安排、一句修改。
- 上线后修复全部完成后，按[线上实测清单](../tasks/phase1/postlaunch.md#线上实测清单)用真实配置完整检查一遍，再请用户实际使用一天。
- 以后拆任务时，单独列出这个任务依赖的适配层和环境默认值，并逐项确认。
