# 第 2 批：结构化抽取（契约）

**先读 [并行方案与数据约定](../parallel.md)，再读本页，最后读自己的任务包。** 本页是这一批的规则和验收序列。本页和任务包冲突时以本页为准，并立刻告诉协调者。

## 1 这一批做什么

每份资料抽出：谁、在哪、什么时候说的、说的是什么时候的事、是事实、偏好、意向、计划还是决定。同一个人、同一个地点在不同资料里是同一个对象，「我」始终是用户本人。新资料自动处理，旧资料慢慢补做。

**上线后用户能感受到的变化**：对秘书说「下周去成都，想吃春熙路那家火锅，顺便见老王」。资料库里多出几条记忆，卡片上写着「成都」「老王」和「下周」对应的日期；在资料库里点「老王」，能看到所有提到他的记忆。以前说过的话也会陆续被整理出来。

## 2 现在的事实

- 抽取（`processing.go` 的 `ProcessExtraction`）只产出一段文字、一个主体名和性质。主体在每份资料里各建一个 `unknown` 实体，两份资料里的「我」不是同一个对象。没有地点、人物，没有时间。
- 记忆的「什么时候说的」没有写：新陈述的 `expressed_at` 是空的。
- 对秘书说的话抽出来的记忆一律是「待确认」；只有速记里逐字、高置信的直接表达才算「原话有据」。待确认的记忆只给打开了「包含推测」的副手。
- 一句话既是待办请求又是计划时（「周五三点和张三对方案」），通常只当成待办，记忆里不留。
- 后台任务失败一次后重试，如果重试时通道暂时不可用，会被判成「通道未配置」而永久停住（待办第 18 项）。超出每日预算的任务也是停住而不是顺延。
- 记忆列表（`memoriesTx`）每条记忆单独再查三次库，并且整份塞进每次返回的工作台快照。记忆变多之后每一轮对话都会变慢。
- 线上现状（2026-10-02）：43 份资料，1 条记忆。

## 3 规则

### 抽取（E1）

**R1 模型输出的形状。** 在现有每一项的字段之外增加：

```json
{ "people": ["老王"], "places": ["成都", "春熙路"], "organizations": [],
  "when": { "from": "2026-09-14", "to": "2026-09-21", "precision": "range", "quote": "下周" } }
```

`when` 没有就不写。`precision` 是 `day`、`month`、`year`、`range` 之一。其余字段和现在一样。提示词里把「说这句话的时间」和用户的时区一起交给模型。

**R2 什么算记忆。** 用户说出的事实、偏好、决定、意向、计划都产出记忆项，即使同一句话同时也是在请秘书建待办。纯提问（「我去成都想吃什么」）和只操作事项的话（「改到四点」「撤销」「这件做完了」）不产出记忆。对秘书说的话里的待办和想法项照旧不建候选（秘书已经执行过了）。

**R3 主体。** 用户角色的资料里，第一人称的主体是用户本人的那一个实体（类型 `self`，每个用户恰好一个，没有就建）。主体是别人时按 R4 的办法找到或新建 `person`（或 `organization`）实体。说不清主体的照旧。AI 角色的资料照现在的处理，不变。

**R4 提到的人、地点、机构。** 每个名字：

- 必须逐字出现在这份资料的正文里，或者出现在交给模型用来解指代的相邻消息里；否则丢掉这个名字，这一项照常保留；
- 去掉首尾空白后长度 1–40 个字符；每一项每类最多 8 个，多的丢掉；
- 「我」「我们」不算人名；
- 按数据约定第 3.2 节找到或新建实体，写进 `claim_mentions`。

**R5 什么时候说的。** 记忆的 `expressed_at`：资料自己有表达时间就用它；没有、但资料是用户亲手输入的（对秘书说的、速记、Telegram、未完成的秘书原话），用资料的记录时间；其余情况留空。未知就是未知，不拿导入时间顶替。

**R6 说的是什么时候的事。** `when` 写进 `event_from`、`event_to`、`event_precision`：

- `when.quote` 必须逐字出现在正文里；
- 相对的说法（下周、明天、去年）由模型按「说这句话的时间」换算；不知道说话时间的资料，相对说法不换算，不写事件时间；
- 存成左闭右开的区间，按用户时区取整：`day` 是那一天，`month` 是那个月，`year` 是那一年，`range` 是给出的起止日；一天之内的几点几分不保留；
- 不合法的（不是日期、止早于起、跨度超过 10 年）丢掉 `when`，这一项照常保留。

**R7 哪些直接可用（用户决定 10）。** 同时满足下面几条的记忆标成「原话有据」（`adopted`），不用用户再点确认：资料是用户亲手输入的、说话人是用户、是直接表达（不是转述和推断）、没有「可能、也许、考虑、如果」这类限定（沿用现有的判断）、置信度不低于 0.8。其余一律「待确认」（`candidate`）：导入的旧聊天、转述、推断、带限定的话。不再要求记忆文字和原话逐字相同。

**R8 重复处理不重复记。** 同一份资料的同一个版本被再次处理（重试、补做）时：

- 这一项引用的原话片段，和这份资料已有的某条记忆的证据片段完全相同：不新建记忆。那条记忆如果是 AI 写的版本，把人、地点、事件时间补上去，`expressed_at` 为空时补上；**不升版本**，所以用过它的回答不会因此变成「依据已更新」。
- 那条记忆被用户改过或确认过：不动它。
- 现有的按「主体 + 属性 + 文字」去重、纠正重定向、重导入阻断照旧生效。

**R9 处理结果要留记录。** 每份资料版本处理完，在 `source_extractions` 里记一行：抽出了记忆是 `done`，什么都没抽出是 `empty`，最终失败停住是 `failed`；`extractor` 写 2。长资料分成多段处理的，全部段处理完才算完。分段沿用现在的做法，不改：每段 12000 个字符，每次往后挪 11000 个字符，相邻两段重叠 1000 个字符（第一段是第 0–11999 个字符，第二段从第 11000 个字符开始）。`items` 是这份资料这个版本最后留下的**不重复的记忆条数**，不是各段返回项数的总和：重叠区里同一句话两段都抽到，只算一条。

**R10 第 1 批的规则不变，外加一条省钱的。** 整轮撤销的那句话不抽记忆；上传归档里的旧话不变成今天的待办；`actions`、`corrections`、`memory-input` 三类不抽取；抽不出东西的资料，原话照样能被秘书和副手找到。

新增：上传归档里 AI、系统、工具角色的消息**不调模型抽取**，处理记录直接记 `empty`。它们的原话照样存着、照样能被找到，也照旧作为相邻消息帮用户说的话解指代。一份聊天记录里一半是 AI 说的话，这一条省掉一半的调用。

### 后台队列和补做（E2）

**R11 先做新的。** 领取后台任务时 `priority` 小的先做，同级按原来的顺序。补做旧资料的抽取任务是 10，其余是 0。

**R12 失败怎么重试。**

| 失败 | 错误类型 | 处理 |
|---|---|---|
| 没有配置抽取用的模型 | `provider_not_configured` | 立刻停住，等用户配置后手动重试 |
| 通道暂时不可用（请求没有发出去） | `provider_unavailable` | 自动重试，间隔 1 分钟、5 分钟、15 分钟、1 小时；第 5 次还不行才停住 |
| 模型调用失败、模型输出不合格 | `model_call_failed`、`model_output_invalid` | 按次计费的通道不自动重试（可能已经扣费），和现在一样；订阅通道按上一行的间隔重试 |
| 超出每日预算 | `budget_deferred` | 不算失败，不消耗重试次数；顺延到用户时区的第二天零点之后再做 |

停住的任务保留现有的手动重试。E1 负责在 `processing.go` 里返回对的错误类型，E2 负责 `worker.go` 里按这张表处理。

**R13 补做旧资料。** 后台每 10 分钟看一次：

- 找出「当前版本、有可读文本、不是三类系统记录、还没有 `extractor ≥ 2` 的处理记录」的资料，从新到旧，每次最多排 20 个抽取任务（`priority` 10）；
- 队列里等着的补做任务已有 20 个时不再加。这里和下面的 30 都按**资料**计数：一份长资料被拆成多段处理，只算一个；
- 任意连续的一小时内最多**排入** 30 个补做任务（按排入的时间算）。新进来的资料不受这个限制；
- 两个后台进程同时跑也不会重复排同一份资料。

**R14 导入的资料。** 属于上传归档的资料，抽取任务一律 `priority` 10。所属导入批次处于 `paused` 时，它的任务不被领取；恢复后照常领取。

### 记忆库（M）

**R15 记忆带上新字段。** 记忆对象里填上 `expressedAt`、事件时间、`mentions`（数据约定第 3.3 节）。读一批记忆只用固定次数的查询，不随条数增加。

**R16 列表和筛选。**

- `GET /v1/workspace/memories`：参数 `q`（文字）、`entity`（实体 id）、`nature`、`from`、`to`（按说话时间）、`cursor`、`limit`（默认 50，最大 100）。返回 `{ "items": [...], "next": "…", "total": n }`，按最近更新排序。翻页期间有新记忆进来，已翻过的不重复、不漏。
- `GET /v1/workspace/memories/{id}`：取一条。
- `GET /v1/workspace/memory-facets`：`{ "people": [{ "entityId", "name", "count" }], "places": [...] }`，各取记忆数最多的 50 个。
- 只有用户本人能调。已删除的不出现。
- 工作台快照里的 `memories` 只放最近更新的 200 条，`memoryTotal` 是总数。**秘书和副手不受这 200 条限制**，它们照旧能用到全部符合条件的记忆。

**R17 撤销只标记（用户决定 8）。** 撤销秘书的动作连带删掉一条记忆时（第 1 批 R9），之前用到这条记忆的回答、副手结果**不清空**：回答原样保留并带 `outdated: true`，给模型的历史里换成替换语（第 1 批 R7）。用户明确删除一条记忆或一份资料时仍然清空，不变。

**R18 后来启用的副手（待办第 21 项）。** 一个副手第一次被启用时，把所有「至少对一个副手开着」的有效记忆对它打开，并在这个副手上记下已经开过。对所有副手都关着的记忆保持关着。之后用户再关掉某条记忆，重复启用停用不会把它重新打开。上线时已经启用的副手直接记为已经开过，不补开。

**R19 删除收尾和导出。** 删掉记忆之后，AI 建的实体如果没有任何记忆再提到它、也不是任何记忆的主体，就一起删掉（连同别名）。用户本人的实体永远不删。导出全部数据时，把这一阶段新增的表（`claim_mentions`、`source_extractions`、`import_batches`、`model_usage`）和陈述上的事件时间一起导出。

**R20 纠正时带着走。** 用户改一条记忆的文字产生新版本时，旧版本上的人、地点、事件时间原样带到新版本。

**R21 新的错误类型要有人话。** `provider_unavailable`、`budget_deferred` 在「后台有事没做完」的提示里各有一句说明和处理建议。

### 界面（U2）

**R22** 记忆卡片上能看到人、地点、什么时候说的、说的是哪天的事。资料库的记忆列表从新接口翻页读取，能按人、按地点、按性质筛。别的页面用到记忆的地方在超过 200 条时仍然正常。

## 4 操作序列

T2 按这张表写测试，一条至少一个测试，测试名带编号（`TestPhase2B2_X1_…`）。除特别说明外，模型是假服务，回答由测试写死。

### 后台队列和补做

| # | 操作 | 预期 |
|---|---|---|
| F1 | 先排一个补做任务，再进来一份新资料 | 新资料的任务先被领取 |
| F2 | 订阅通道：第一次模型输出不合格，第二次通道暂时不可用，第三次成功。再测一种：连续 5 次通道不可用 | 第一种：任务最后完成，记忆写入，没有被停住。第二种：第 5 次之后停住，类型 `provider_unavailable`，可以手动重试 |
| F3 | 没有配置抽取模型 | 立刻停住，类型 `provider_not_configured`；配置好之后手动重试成功 |
| F4 | 按次计费的通道，今天预算已用完 | 任务没有停住，没有消耗重试次数，顺延到用户时区第二天零点之后；到时间后完成。换一个时区再测一次 |
| F5 | 50 份没处理过的旧资料，连续跑三次补做检查（每次之间把排好的任务处理完），再把时间往后拨一小时跑一次；其中有 `actions` 资料和已经处理到 2 的资料 | 等着的补做任务任何时候不超过 20 个；同一个小时里排入的不超过 30 个，过了一小时又能接着排；`actions` 和已处理的不被排；两个后台进程同时检查，同一份资料不被排两次 |
| F6 | 一个导入批次暂停，另有一份普通新资料 | 暂停批次的任务不被领取，普通资料照常处理；恢复后被领取 |
| F7 | 抽取做到一半后台进程被杀，租约过期后重新领取 | 最后记忆只有一份，不重复 |
| F8 | 按次计费的通道，模型调用失败 | 不自动重试，停住，和现在一样 |

## 6 给验收用的固定入口（2026-10-02 补充）

T2 需要可以直接调用、可以控制时间的入口。这几个名字和参数冻结，由 E2 提供：

| 入口 | 位置 | 含义 |
|---|---|---|
| `func (s *Store) BackfillExtractions(ctx context.Context, now time.Time) (int, error)` | `backfill.go` | 做一次 R13 的补做检查，`now` 用来算「一小时内排了多少」，返回这次排入的任务数。后台每 10 分钟用当前时间调它 |

## 7 第二轮补充（2026-10-02）
