## 要交付什么

### 1 一份虚构的人和他的记忆（进仓库）

一个虚构的人，至少 600 条记忆，跨 6 个月，覆盖学业或工作、一两个自己在做的项目、租房和日常、几个有名字的人、对助手的要求。要有这些难点，并在数据里标出来：

- 同一件事说过多遍（重复）；
- 先后说过不同的说法（期限改了、决定推翻了、授权收回了）；
- 两个同名的人、一个人的两种叫法；
- 一次性的琐事占相当比例；
- 对助手的要求散在各处（发出去之前先看、别啰嗦、只做必要修改）。

可以用模型帮忙生成，但每一处「后来改了」和每一条要求要人工看过，确保数据本身没有矛盾到无法判断。

### 2 至少 120 个任务（进仓库）

六类，每类至少 20 个：

| 类 | 例子（虚构） |
|---|---|
| 直接回忆 | 「我们给汇报定的三个指标是哪三个」 |
| 间接用到 | 「帮我排一下下周」（要用到期限和固定安排，话里没提） |
| 跨分组 | 「给小陈回个消息，约个时间对数据」（要用到人、项目、日程、对助手的要求） |
| 旧说法已更新 | 请求会碰到一个后来改过的事实 |
| 往外发的动作 | 起草邮件、消息（要用到「发之前先给我看」这类要求） |
| 无关记忆干扰 | 和记忆基本无关的请求，看它会不会硬套个人情况 |

每个任务人工写好：

- **必须**：结果里一定要体现的情况，每条只含一件事，附它依据的记忆编号。3–6 条。
- **加分**：体现了更好、没有也不算错的。
- **不许**：不能出现的做法或说法（用了被替代的事实、替他直接发出去、编造他没说过的情况），附依据。
- 这个任务在不追问的情况下能不能做完。不能做完的，写明合理的做法是什么（先拟草稿并说明缺什么）。

不要出前提不完整的题（要求「核对来信」却没有来信）。

### 3 跑法

`pcas-eval` 加一种模式，对一个装好数据的一次性数据库：

- 每个任务用若干种「交给模型的内容」各办一次。先内置三种对照：什么都不给、线上现在的检索（秘书真实走的那条路）、直接给「必须」所依据的记忆（理想证据）。后面各批的新做法作为第四、第五种接进来，接口要留好。
- 办事的方式固定并写进报告：同一段指令、同样的字数上限、同一个模型。
- 打分：对每个任务逐条判「必须」「加分」「不许」。打分的指令固定。每个回答判两遍，不一致的单独列出。
- 报告：每种做法的「必须」体现率、「不许」触犯数、可直接用的比例、给模型的字数、模型调用次数、每个任务的耗时；按六类分别给；给出同一种做法重复跑三次的波动范围，据此写明「相差多少以内不能算差别」。
- 有假模型模式供 CI 跑通流程；真实通道模式在本机手动跑。

### 4 真实数据上的跑法（不进仓库的部分）

部署主机上有用户的真实记忆。提供一个只读的本机流程：

- 从线上库导出记忆到一个仓库之外的目录；
- 让模型按六类各出若干任务和标准答案，写成一个便于人看的抽查表（每题：请求、必须、不许、依据的记忆原文）；
- 用户在抽查表里勾「对 / 不对 / 改成…」，只有勾过的题进入评测；
- 评测结果只输出数字和题号，不输出记忆正文。

这个流程的脚本进仓库；它产生的任何文件都不进仓库，默认输出目录在仓库之外，并在 `.gitignore` 里加一道保险。对线上库只读。

## 不要做的

- 不改产品代码（`internal/` 下除评测自己用的包之外）。需要产品暴露什么才能测，告诉协调者。
- 虚构数据里不要出现任何真实的人名、机构名、地址和线上内容。
