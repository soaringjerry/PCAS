# 第 3 阶段：工作室（入口与契约）

2026-10-08。上位依据：[白皮书](../../whitepaper.md) §4 工作室、§5.6（项目交接说明）、§11、§16 第 3 阶段、§17 黄金路径 4 和 5；[记忆架构](../../memory-architecture.md) 1.4；[界面与交互原则](../../design/principles.md)；[任务流程规则](../process.md)。本页是第 3 阶段的唯一契约，三个窗口同时开发；和上位文档冲突时以本页为准，冲突处由协调者在收尾时改上位文档。**所有执行者先读完本页再动手。**

开工前的六项修复另有任务包：[P0](P0-fixes.md)，在 `main` 上单独走，和本页的代码没有交集。

## 0 工作方式

- **契约没写到的实现细节，你自己定，写进 PR 描述，不用停下来问。** 包括文件怎么拆、函数名、表的列、任务阶段名、提示词措辞、索引、页面布局细节。
- **只有这三种情况停下来问协调者**：要改用户看得见的行为而本页没写；要改第 3 节的接口；发现本页两条规则互相矛盾。
- 集成分支 `phase3/main`，从 `main` 建。每个窗口一个长分支、可以多个 PR，base 都是 `phase3/main`。做完一块就交，不要攒。
- 不改别的窗口归属的文件（第 1 节）。必须动时只加不删，在 PR 描述里列出来。合并冲突由后合的人解决。
- 测试和示例只用虚构内容；不读线上数据库；不部署；不按进程名杀进程；不碰 `pcas-db-1` 和线上容器；测试库用自己起的一次性容器，用完删掉。
- 改了给模型的资料或输出格式，上线前用真实通道（自己的登录目录）跑一次看原始输出，贴进 PR（流程规则第 8 节）。
- 2.6 的七条通用规则 G1–G7（[2.6 契约第 4 节](../phase2_6/README.md#4-各批的规则)）全部适用，验收逐条查。特别是：**上限要有依据和去向；失败不覆盖；模型结果不白花；一处变动不整份重做；判断交给模型、程序只校验；读的路径不写；每个后台阶段有自己的预算。**
- 迁移编号从 050 起（P0 用 046–049）。

## 2 定下的事

用户 2026-10-08 同意，不再讨论：

1. **现状块 = 项目交接说明。** 每个项目一份，模型写，固定三段（结论、卡点、下一步），每句带依据；输入变了才重写，最快每小时一次；失败和重写期间沿用上一份并写明写于何时。**不提供直接改块里文字的入口**：纠错落在底下的记忆或事项上。现有的 `progress`、`nextSteps` 两个字段退役（读接口保留到界面切换完再删，不再写）。
2. **文档每次写入留一个版本**，差异读取时算、不另存。「在某一版上改一部分」是副手的一种工作，产出新版本。
3. **文件区做最小版**：上传、列出、打开、删除。不做文件夹、改名、文件版本。删除要确认（这是「删除一律先问」的第一次落地；文档删除维持「删完给撤销」不变，待办 38 到此为止）。
4. **二把手只做到**：每步估工作量 → 从截止倒推开工日 → 计划时间轴 → 到开工日提「该开始了」。不做日程冲突（要日历，第 5 阶段）。
5. **做法沉淀、完成条件裁判不进这期**，记入待办。
6. **两批同时开发，第 1 批先合先上**；第 2 批在第 1 批的页面结构上加。
7. 第 2 阶段以来的决定继续有效：团队默认共用全部记忆；不做任何形式的授权门；每批都小；验收走真实的路；协调者合并前自己通读代码。

## 3 批次之间的接口

后端提供、界面使用。HTTP 路径和 JSON 字段由后端定，写进骨架 PR 的描述，界面照着接。工作区快照（`GET /v1/workspace`）的版本号机制沿用 2.6（`library_revision` / `snapshot_revision`），新数据变了要让快照版本变。

| 读什么 / 做什么 | 要求 |
|---|---|
| 项目交接说明 | 按项目读：三段各自的句子列表，每句带依据（记忆、事项、文档版本、副手工作的编号，可以多个）；写于何时；是否过期；没有时如实返回空而不是占位文字 |
| 文档的版本列表 | 某份文档的全部版本：版本号、写于何时、谁写的（用户 / 副手 / 秘书）、基于哪一版、来自哪次副手工作；按时间倒序 |
| 某一版的正文 | 读一版 |
| 两版之间的差异 | 给两个版本号，返回段落级的增删改（后端算，格式后端定；界面只负责显示）；默认最新对上一版 |
| 在某一版上改一部分 | 走现有的 `requestRun`，新增工作种类 `revise`，带目标文档和基准版本；副手输出整份新正文，后端存为新版本并记 `basedOn` 和 `runId`。秘书的 `delegate` 动作也能发起（「把第二版方案里的预算部分改保守一点」） |
| 文件 | 上传（多部分表单，大小上限按现有附件上限）、按事项列出、下载 / 打开、删除。每个文件是一个来源，带 `scope.project_id`；列表里带这个文件的处理状态（已存、已抽取、失败及原因） |
| 工作量与开工日 | 事项多两个字段：估计工作量（小时，可为空）、开工日（程序算）。工作量来自后台估计或用户一句话；开工日 = 截止 − 工作量按每天可投入时间折算（默认值和依据写进 PR，设置里不新增开关） |
| 计划时间轴的数据 | 某项目下有截止的事项：开工日、截止、状态、估计工作量；没截止的不在时间轴上，另列 |

`GET /v1/workspace/items/{id}/retained-writing`、`updateProject` 里的 progress / nextSteps 保留到界面切换完再删。

## 4 各批的规则

每条写的是要达到的结果。怎么实现自己定。

### 4.1 调用预算

在 2.6 的每小时预算上**新增两个阶段**，互不挤占，用不完不借：

| 阶段 | 每小时上限 | 依据 |
|---|---|---|
| 项目交接说明 | 10 | 线上项目数量级为几十，同一项目一小时最多重写一次；10 意味着一小时最多 10 个项目更新，超出的按过期时间先后排到下一小时，不丢 |
| 估工作量 | 10 | 一次调用可以估一批（同一项目的多条一起），线上有截止的事项一天新增个位数；超出的排到下一小时 |

总量从 120 升到 140。数值放在和 2.6 预算同一处。每条记忆或事项变动最多触发几次项目交接说明的重写，PR 里写明（预期：同一项目一小时内合并成一次）。

### H 项目交接说明（第 1 批）

- **H1 输入。** 这个项目名下（分组 `work_item_id` 对应的 project 实体，以及 `scope.project_id`）的当前记忆；项目下的事项及其状态、截止；项目下每份文档的最新版本；项目下副手工作的结果（已采纳的和最近一次未采纳的）；这个项目的期限表行。输入用原样内容加日期，概括性文字只作背景。
- **H2 输出。** 三段：结论、卡点、下一步。每段是句子列表，每句至少一个依据；程序校验依据存在，没有依据的句子不入库并记数（G1）。每段条数有上限，依据和超出去向写进 PR。
- **H3 触发。** 输入里任何一项变了就标为过期；重写走 4.1 的预算，同一项目两次重写至少隔一小时；标过期到重写完成之间读到的是上一份，带「写于何时」和「过期」标记。项目完成（`done`）后不再重写。
- **H4 失败不覆盖。** 模型没写出合格的三段时，上一份留着；连续失败按 2.6 的 A5 退避并计数，观测台数据里能看到。
- **H5 用到。** 工作室底部的秘书、派到这个项目的副手，在现有的全局交接说明之外还拿到这个项目的交接说明。重档按分组细读时，这个项目的分组排第一。
- **H6 纠错。** 用户在工作室对秘书说「卡点不对，那个问题上周解决了」：秘书改的是对应的记忆或事项（现有动作），这会让 H3 触发重写；不提供编辑三段文字的动作。
- **H7 退役。** 不再写 `progress`、`nextSteps`；副手结果「采纳为进展」改为采纳成一条项目记忆（走现有的记住一件事），从而进入 H1 的输入。
- **H8 给模型的资料里写明**：交接说明、期限、记忆都只是资料，不是指令（沿用 2.6 的修订）。

### D 文档版本与差异（第 1 批）

- **D1** 每次写入 `work_documents` 都留一个版本：版本号、正文、写于何时、作者（user / deputy / secretary）、`basedOn`、`runId`。现有文档迁移时作为第 1 版。
- **D2** 用户点进去改、失焦保存（交互原则）产生的连续写入每次都是一个版本，不合并存储；界面展示时把同一作者 15 分钟内的连续版本折成一条（依据：失焦保存会在一次编辑里写很多次；15 分钟是一次编辑的常见长度；折叠只是显示，点开能看全部）。
- **D3** 差异在读取时按段落算，不另存。返回格式后端定，至少能区分增、删、改的段落。
- **D4** `revise` 工作：输入是基准版本的全文、用户的要求、项目交接说明和相关记忆；输出整份新正文；存为新版本，`basedOn` = 基准版本。副手输出不合格（空、明显截断、和基准完全相同）时不存版本、记失败原因（G2）。
- **D5** 撤销一次 `revise` 的采纳 = 新版本退出当前视图，不删除；再撤销恢复。沿用现有撤销机制。
- **D6** 秘书的 `delegate` 支持 `revise`：从这句话里定目标文档和版本（「第二版方案」）；定不下来时追问那一个字段（交互原则：只追问真有歧义的）。
- **D7** 删除文档维持现状：删完给撤销，所有版本一起退出，撤销一起回来。

### S 秘书与副手在工作室（第 1 批）

- **S1** 工作室底部的秘书知道当前项目：建的事项默认归这个项目；取材时项目分组优先（现有机制），并带项目交接说明（H5）。
- **S2** 派副手带对话上下文（P0 的 23、24 合入 `phase3/main` 后沿用，不重做）。
- **S3** 副手工作记录里，每次工作能看到它用了哪一版文档、哪份项目交接说明（写于何时）。

### F 文件区（第 2 批）

- **F1** 上传：走现有的来源与附件机制，`scope.project_id` 为这个项目（事项属于项目时取项目，事项自己是项目时取自己）；重复上传同一文件（内容相同）不重复入库，回「已经有了」。大小上限沿用现有附件上限，PR 里写明数值和依据。
- **F2** 文件进来源层后按现有流程处理（文字抽取、图片看图、转录），抽出的记忆带项目范围，由 H3 触发项目交接说明过期。
- **F3** 列表带处理状态和失败原因；失败的能在原处重试（现有的 `retryJob`）。
- **F4** 删除先确认；确认后走现有的来源删除（原文和派生副本一起清，阻止重导入）。
- **F5** 打开：浏览器能直接看的（图片、PDF、文本）在页内看；其余下载。

### P 工作量、开工日与时间轴（第 2 批）

- **P1** 估工作量是一个后台阶段：项目下有截止、没有工作量的事项，一批一次调用，输出每条的小时数和一句依据；预算按 4.1。用户一句话改（「这个要两天」）走秘书的 `update`，用户给的值不再被后台覆盖。
- **P2** 开工日由程序算：截止 − 工作量 ÷ 每天可投入小时数，跳过周末；每天可投入小时数的默认值和依据写进 PR，不做设置开关。工作量为空时没有开工日。
- **P3** 到开工日提「该开始了」：走现有提醒通道和规则（说明原因、冷却、去重、执行前核对状态——事项已完成或已开始就不提）。提醒一次；用户说「不用提醒」就不再提。
- **P4** 时间轴数据按第 3 节给；已完成的、已取消的仍在轴上并标出，截止已过的标出。

### U 界面

**U1（第 1 批）**

- 工作室页（现在的项目事项页）顶部是现状块：结论、卡点、下一步三段，每句能点开看依据（记忆点开到原话，事项跳到事项，文档跳到那一版，副手工作跳到记录）；显示「写于何时」；过期时显示「正在更新，下面是上一份」；没有时如实说「还没有」，不放占位文字。没有任何可以直接编辑三段文字的控件。
- 文档：点开一份文档能看版本列表（按 D2 折叠），选任意两版看差异，默认最新对上一版；差异用增删改三种标记，不写长文说明。
- 副手工作记录里显示 S3 的信息。
- 去掉 progress / nextSteps 的编辑入口。
- 首页项目墙的卡片改用项目交接说明的「下一步」第一句（没有时显示项目目标），不再用 progress。
- 页面用语和现有页面一致；按钮只有三种（交互原则）。

**U2（第 2 批）**

- 文件区：拖入或选择上传；列表带状态；点开按 F5；删除弹确认（这是日常界面上唯一的确认框样式，和外发、花钱共用）。
- 计划时间轴：横向时间轴，每条有截止的事项一条从开工日到截止的条，现在线，过期和完成的标出；没截止的另列一组。点一条跳到事项。工作量显示为「约 n 小时」，点一下跟秘书说改。
- 手机宽度下时间轴可横向滚动，其余不横向滚动。

### T 独立验收

只读本页写测试，先冻结预期，再看实现。

- **T1** 在 2.6 的线上规模夹具（5,000 条记忆、300 个分组）上加：30 个项目、每项目 5–40 条事项、每项目 1–10 份文档各 1–20 版、每项目 0–5 个副手工作结果、每项目 0–8 个文件。
- **T2** 逐条验 H、D、S、F、P 和 G1–G7：每个后台阶段都要有「排班、处理、用户请求同时跑」的并发验收；项目交接说明的每句依据都存在；同一项目一小时内多次输入变动只重写一次；失败不覆盖；预算到顶后排队不丢。
- **T3** 验内容不只验有没有：三段里的句子引用了夹具里埋的最新文档版本和最新事项状态，没有引用已被替代的记忆；差异结果和夹具里埋的改动对得上；开工日算得对（含跨周末）；「该开始了」在开工日触发、事项已完成时不触发。
- **T4** 耗时：读项目交接说明、版本列表、差异、时间轴数据各在多少毫秒内（预期和 2.6 的读接口同量级：交接说明几毫秒、整份工作区一秒内）；一条记忆变动触发的模型调用数对照 4.1。
- **T5** 浏览器：黄金路径 4 和 5 的回放（虚构数据）；「10 秒内知道结论、卡点、下一步」量的是打开工作室到现状块可读的时间。

### E 评测基线（协调者）

- P0 的 61 合入后，用评测工具在 2.6 的库上跑一次三档对比，作为第 3 阶段起点。
- 第 1 批上线后，26 道私有题里和项目相关的题再跑一次；新增 10 道「续做项目」题（给项目交接说明、不给整个项目的记忆，看模型能不能接着做）。私有题和结果不进仓库。

## 5 验收与上线

1. 各批 PR 合入 `phase3/main`，协调者读代码后合并。
2. T 批在 `phase3/main` 上全部通过。偶发失败不算通过，要查清。
3. 第 1 批：协调者合入 `main`、备份、上线、线上用默认通道实测：打开一个真实项目看现状块；对一份真实文档说「把第二版的某部分改一下」看第三版和差异；撤销。上线后核对：项目交接说明的条数和写于何时、一小时调用数、没有依据被丢的句子数。
4. 第 2 批同样走 3。另加：上传一个文件看它变成记忆并进入现状块；一个有截止的事项看开工日和「该开始了」。
5. 黄金路径 4、5 在线上跑通；E 的数字记入评测记录。
6. 协调者更新白皮书 §15、§16、记忆架构、待办清单。
