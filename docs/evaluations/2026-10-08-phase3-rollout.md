## 3 独立验收的发现与修法

验收 #266 冻结了 T1–T5 的预期；第一次在合并后的 `phase3/main` 上强制跑（`PCAS_PHASE3_RUN_FINDINGS=1`），27 项里 12 过、15 挂、40 分钟超时。逐条定位后分两类：

**产品问题（协调者修，提交 8ff5e82）**

| 发现 | 原因 | 修法 |
|---|---|---|
| 归类、比较的后台写入在 5,000 条记忆的库上要 4.8 秒，超过 2 秒的后台写入上限；重试时落在被 pgx 关掉的专用连接上报 `conn closed` | 迁移 050 给十张表加的逐行触发器，每改一行就从「全部项目」出发扫一遍 `entity_versions` 找这条记忆属于哪些项目（30 个项目 × 约 1,000 个实体） | 迁移 053：触发器改为提交时触发（DEFERRABLE INITIALLY DEFERRED），同一事务里每条记忆只查一次；查法改为从记忆自己的范围、主体和提到的实体出发。关掉的专用连接不再在进程内重试，交还任务 |
| 连续撤销两次改写（A→B→撤 B→撤 A）被拒 `newer_action` | D 批把「撤销一次改写采纳」记成一个新动作（这样才能再撤销恢复），这个记录被当成 A 之后的「更新动作」 | `action_log.undo_of` 标明它撤的是哪个动作；核对后继动作时跳过撤销记录。旧的撤销规则测试全部仍过 |
| 每小时总上限还是 120 | 契约 4.1 定 140 | 改 140 |
| 删文件返回 204 | 冻结接口写的是 200 `{"deleted":true}` | 改回 |
| 上传的 `.txt`/`.png` 被判「没有解析器」 | 浏览器和测试常给 `application/octet-stream`，解析器按媒体类型选 | 先按扩展名、再按前 512 字节嗅探 |
| 文件列表只在失败时给 `jobId` | 页面要跟进和重试 | 有处理任务就给，状态仍按任务状态算 |
| 手动粘贴的改写结果绕过 D4 校验 | 粘贴路径没有模型的 `complete` 标志 | 空、和基准或当前版相同、短于基准四分之一（基准不少于 40 字）的不存版本，原因记在 run 上，仍可再贴 |

**验收适配器和公开接缝不一致（协调者改测试）**

估工作量的排班入口是 `ScheduleStatus` 而不是 `ScheduleEffort`；任务键在 `stage` 列里，没有 `dedupe_key`；验收的 HTTP 服务没挂附件路由；模型假回复的工作量用 `id` 而产品要 `itemId`；秘书改写要用目录里的 `D*` 别名而不是 UUID；「再撤销恢复」是撤销那条撤销记录，不是对同一个动作再撤一次（已批准的规则：重复撤同一个动作返回 `already_undone`）。
