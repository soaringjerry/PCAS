# Q5 后台在用模型时，秘书偶尔「模型没有响应」

2026-10-05。执行者 6.1 Sol。分支 `fix/q5-secretary-model-error`，从 `origin/main` 建；工作区 `/root/PCAS-wt/q5`；Draft PR 的 base 是 `main`。

## 现象

线上连着说三句话（间隔几秒），五轮里有两轮的第二句得到回执「已记下原话；模型没有响应，稍后会自动整理」，事项没有建出来。接口日志只有一行：`secretary capture fallback stage=model error_type=model_error`，约 9 秒就返回，不是超时。同一时间后台 worker 正在抽取上一句话（`model_usage` 里同一分钟有 extraction 记录）。后台整理当时因每小时上限停着，所以不是整理造成的。

[P2](P2-turn-speed.md) 上线前同样的三句话连说两轮没有出现。P2 没有改模型调用；它让一轮从三十秒降到十几秒，于是第二句开始时上一句的抽取还没结束。这是推测，需要验证。

以前记过同类问题（待办第 18 条：秘书和后台同时使用 Codex 时偶尔失败，原因没有确认），当时只给后台抽取加了自动重试，秘书这一侧没有处理。

## 已知的结构

- 接口进程和 worker 进程各有一个 Codex app-server 子进程，共用同一个登录目录（`PCAS_CODEX_HOME`）和同一个订阅账户。
- 秘书失败后不重试，直接走「记下原话」的兜底。

## 要交付什么

1. **找到真正的错误。** 现在只记了 `model_error`。先让失败时记下不含正文和凭据的具体类别（Codex 返回的错误码或类别、是哪一步、耗时），然后在本地复现：一个进程连续调用模拟后台，另一个进程同时发秘书请求，共用一个登录目录。确认是账户并发限制、登录凭据刷新时互相覆盖、还是别的。
2. **按原因修。** 原则：
   - 用户说的话不能因为后台在忙就办不成。可重试的失败，秘书应当在一轮的时限内自动重试（次数和间隔你定，写明总时限），重试期间不重复写任何东西。
   - 如果是两个进程抢同一份登录状态，要从根上解决，不要只靠重试盖住。
   - 后台任务让路给秘书是可以考虑的做法，但不能让后台饿死。
3. **回执要准。** 重试后仍失败才显示「模型没有响应」；[界面与交互原则](../../design/principles.md) 要求出错说清楚原因。
4. 一条能稳定复现原问题的测试（修之前失败、修之后通过），和一个在真实通道上的走查：后台连续抽取的同时连着说十句话，记录成功数。

## 不要做的

- 不用线上数据，不碰线上容器和线上的登录目录。真实通道走查用自己的登录目录。
- 不改秘书的提示词和动作规则。
- 不部署。

## 交付时报告

真正的原因和证据；修法；修之前和修之后十句话里成功几句；新加的日志字段。
