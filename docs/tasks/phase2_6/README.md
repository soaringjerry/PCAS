## 2 定下的事

以下是用户已经同意的方向，不再讨论：

1. **去掉现状卡。** 不再建卡、不再重建，秘书和副手不再读卡。`status_cards`、`status_card_items` 两张表和里面的数据留着不删，等上线稳定后再清。
2. **「关于你」页面并进资料库。** 记忆只在资料库一个地方看和改。人、项目、主题、领域是资料库的筛选条件。资料库顶部放「眼下」：交接说明和期限表。
3. **期限表有自己的来源。** 记忆归类时由模型一并抽出期限，不新增模型调用。程序只校验「能解析、不早于说话时间」，不再要求和正则算出的日期相等。过了期的留着，标「已过期，不知是否完成」。没说清日期的留着，注明原话。
4. **「对助手的要求」不靠字面匹配。** 全部有效的要求先整组去重。不限范围的每一轮都带。限范围的由模型判断这一轮是否适用，在要求内部排名，不和别的记忆抢名额。
5. **交接说明保留，改输入和节奏。** 输入是：身份、目标、口味里重复说过的和最近说的，全部要求，期限表。输入变了才重写，最快每小时一次。重写期间和重写失败时照常用上一份。
6. **领域可以新增。** 按用户决定 5：给一组初始值，不够时系统自己加。
7. **「一条记忆属于哪些分组」只写一份规则。** 现在的四份（D31）合成一份，其余调用它。
8. **遗忘曲线先不作为依据。** 线上的活跃度现在等于说话时间（D29）。C 批把「用户主动提及」「回答被采纳」记下来并让它参与排序；这之前任何地方不得假设活跃度可用。

## 3 批次之间的接口

后端提供、界面使用。后端开工后先交一个只有签名和空实现的骨架 PR（目标：一小时内），界面等它合入 `phase2_6/main` 再联调，等待期间先做页面结构和筛选的交互。

| 读什么 | 要求 |
|---|---|
| 交接说明 | 返回正文、写于何时、是否过期。过期也返回正文 |
| 期限表 | 返回未到的、已过期不知是否完成的、固定安排、日期没说清的；每行带依据的记忆编号。可按是否过期筛选 |
| 对助手的要求 | 返回去重后的全部有效要求，每条带「不限范围」或范围说明 |
| 某个分组的记忆 | 给人、项目、主题、领域或「关于本人的某一类」，返回它名下的当前记忆，分页 |
| 分组目录 | 全部分组的名字、种类、记忆条数 |

HTTP 路径由后端定，写进骨架 PR 的描述，界面照着接。`GET /v1/workspace/about` 保留到界面切换完再删。

## 4 各批的规则

每条写的是要达到的结果。怎么实现自己定。

### 通用规则（所有批次，验收逐条查）

- **G1 上限要有依据和去向。** 代码里每一个条数、字数、时间上限，在 PR 描述里写明为什么是这个数、超出的部分去了哪里。超出的不许悄悄丢：要么分批处理完，要么记数并在观测台看得到。
- **G2 失败不覆盖。** 模型调用失败、输出不合格、重试用完，都不得清掉或改写已有的好结果，不得把东西标成「已处理」。失败要记原因和次数。
- **G3 模型结果不白花。** 模型调用成功后写入失败，重试写入，不重新调用模型。
- **G4 一处变动不整份重做。** 一条记忆变了，只处理和它有关的部分。
- **G5 判断交给模型，程序只校验。** 不用子串、相邻汉字、关键词表来决定语义上的事。拿不准的留下并标明，不丢。
- **G6 读的路径不写。** 读接口里不改数据。
- **G7 每个后台阶段有自己的调用预算**（第 4.1 节），并写明「一条记忆变动最多触发几次模型调用」。

### 4.1 调用预算（A 批实现，所有批次遵守）

总量维持每小时 120 次不变，按阶段分开，互不挤占：

| 阶段 | 每小时上限 | 说明 |
|---|---|---|
| 归类（含抽期限） | 40 | 新记忆最先处理，优先级排第一 |
| 新旧比较 | 40 | |
| 别名确认 | 30 | |
| 别名名单扫描 | 6 | |
| 交接说明 | 2 | |

用不完不借给别的阶段。数值放在一处，方便以后调。

### A 后台可靠性

- **A1（B4、G3）** 新旧比较、别名确认、名单扫描的结果写入失败时重试写入，不重调模型。
- **A2（B5、D28）** 后台任务被推迟、失败、排班失败，都记原因并计数；观测台能看到每个阶段最近一小时的成功、推迟、失败次数和最近一次失败的原因。同一个任务连续推迟超过 30 分钟要有一条告警级日志。
- **A3（B6、D36）** 按第 4.1 节分预算；归类优先级提到最前。
- **A4（D21）** 「判过了」「扫过了」「失败过几次」这类标记从任务表挪到专门的表。已有的 234 行迁过去，不许丢，丢了就要重新花调用。任务表里已完成的任务可以安全清理。
- **A5（D35）** 比较和归类失败三次后不标成已处理：保持待处理，按 A2 计数，隔一段时间再试，间隔逐次拉长。「不能判断」只在模型明确这样回答时才写。
- **A6（D12）** 超过一次调用装得下的分组，分批比完，批次之间也要比到：很早说过、最近又改口或重复的两条必须有机会放进同一次调用。「比过没有」按「记忆 × 分组」记。「对助手的要求」这类不排在最后。
- **A7（D22）** 别名候选不再用「有一个相同字母」这类规则；候选由名单扫描的模型给出，程序只做类型是否允许合并的校验。判过「不是同一个」的一对，只有其中一方改了名字才重判。名单扫描的「扫过了」标记不随记忆条数变化而失效。
- **A8（B7、D41）** 合并关联很多的实体不超时：分批写，或把写入拆到限时之外。结论是「不是同一个」时不锁卡片。
- **A9（D23）** 每次模型调用记下 token 数；通道不返回时按字数估并标明是估的。按费用算的每日额度对所有通道起作用。
- **A10（D32）** 排班不再每分钟把每一行各写一遍；没有变化就不写。
- **A11（D37）** 一段对话抽出的记忆超过上限时分批收下，不整份作废。
- **A12（B13、B14、B15）** 修排班候选查询超时；修别名并发验收的偶发失败（结束时剩 1 个排队任务）；额度验收 F-B2-8 的夹具只清排队中的任务，去掉跳过。

## 6 上线后的修订（2026-10-07）

2.6 于 2026-10-07 13:11 UTC 上线。上线后的实测查出下面几处，契约随之修订；和前文冲突的以本节为准。

| 原来的规则 | 修订 | 原因 |
|---|---|---|
| 第 2 节第 4 条、C2：限范围的要求每轮都交给模型，由模型判断是否适用 | **限范围的要求不再每轮整批带上。** 每轮只带不限范围的要求；限范围的在相关时随检索带出，留给检索的条数记入观测台（`scoped_requirement_left_to_recall`） | 线上有 335 条，4.2 万字，占一轮资料的一半，排在最前的是被归错类的一次性请求。#255 |
| 无 | 给模型的资料里写明：要求只约束怎么回应这句话，本身不是要办的事；期限表仅供参考 | #254 |
| 无 | 秘书的输出格式说明原样手写，不经解码再编码；有测试按原文核对每种动作的第一个键是 `op` | 2.6 为加 `memoryPlan` 把格式说明经 Go 的 map 重新编码，键被按字母排序，线上模型只能把新建输出成修改或加步骤。#256 |
| A9：订阅通道按估算费用计入每日额度 | 实现不变。线上给订阅通道配置了很低的记账价（每百万 token 输入 0.01、输出 0.04），token 照记，每日额度实际不会被它触发 | 默认估算价下后台一天会超过 100 的额度而停摆，订阅通道本身是包月的 |
| 验收冻结的预期 | 四处随上表修改（每轮带上的要求条数三处、重档的主回答次数一处），测试里注明是协调者上线后改的；五条发现项的跳过开关已去掉 | #252、#255 |

独立验收的五个发现项（S-P26-001 至 005）在 #252 修复。其中 002 的结论要记一笔：后台排班被推迟，等的是用户自己的操作提交时对工作区那一行的锁，这是「后台让前台」的设计。现在排班会短暂重试，仍等不到就跳过这个用户、下一轮再排，并把错过的这一轮连同原因记进观测台。
