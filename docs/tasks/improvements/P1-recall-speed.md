# 任务 P1：资料多了以后，秘书回话不能变慢

2026-10-03 用户导入了 27,399 条聊天记录（1,447 段对话）。协调者在线上实测：导入前秘书回一句话约 6 秒，导入后同样一句短问话 46.5 秒；数据库里那条回忆查询单次执行超过 80 秒的也看到过（当时后台同时在整理）。这是现在最影响使用的问题。

## 原因（查代码确认）

回忆用的查询在 `internal/postgres/retrieval.go` 的 `recallTx`。它对**每一份**资料和记忆都要做这些事，没有先用索引缩小范围：

- 用 `position(lower(词) in lower(正文))` 逐个词在全文里找，每一行都算一遍；
- 对每份资料再挑一个最相关的片段，挑的时候对它的每个片段重复同样的计算；
- 向量相似度逐行计算，没有走向量索引；
- 最后才排序、取前若干条。

资料只有几十份时感觉不到，到几万份就是几十秒。白皮书 5.3（成本原理）要求的是先定位、再细看，这里是全部细看一遍。

## 要做成什么样

**R1 结果不变。** 对同样的库、同样的请求，返回的条目、顺序、片段和现在逐字节相同。第 3 批的 S10（15 组对外检索请求改动前后逐字节相同）继续成立，并且要在一个有几万份资料的库上再验证一遍（用合成数据：把评测工具的压力档材料放大）。

**R2 先定位，再细看。** 先用索引得到候选：关键词用全文索引或三元组索引，向量用向量索引，结构化条件、关联的经历、显式指定的对象照旧。只对候选做现在这套打分和挑片段。候选的取法要保证 R1：凡是现在会进入最终结果的，都必须在候选里。做不到逐字节相同的地方，停下来问协调者，不要自己放宽。

**R3 快。** 在 3 万份资料、15 万个片段的库上（合成数据），一次回忆查询 300 毫秒以内；秘书一轮对话里花在数据库上的时间 1 秒以内。给出改动前后的实测数字和查询计划。

**R4 不拖累写入。** 新增的索引不能让导入明显变慢：导入 1 万条消息的总时间增加不超过一成，给出实测数字。索引用迁移建，线上已有 2.7 万份资料，迁移要能在几十秒内跑完，或者用不锁表的方式建。

**R5 工作区快照。** `Snapshot`（`/v1/workspace`）每次点击都会调用。把它在同一个大库上的耗时也量出来，超过 300 毫秒的部分列出来；这一项只要求测量和报告，改不改由协调者定（资料库来源那一条协调者已经改过，PR #161）。

## 做了什么（2026-10-03，协调者直接做）

用户让协调者直接做。先在线上只读地量出时间花在哪，再改；改完在线上同一个只读事务里把旧查询和新查询各跑一遍，逐字节比较输出。

**量出来的原因**（和上面「查代码」的推测不完全一样，以这里为准）：

1. 数据库对这条语句做即时编译（JIT），光编译就要 1 到 50 秒，比执行还久。
2. 关联「来源」「活跃度」两张表时，数据库估错了行数，选了「每一行都把整张表扫一遍」的做法：2.9 万行各扫一遍 2.7 万行的表，这一步占了 40 多秒。
3. 每一条匹配上的记录都要挑一个最相关的片段（4,681 条），而最后只返回 40 条左右。
4. 逐词匹配时，每个词都把正文重新转一次小写。
5. 带向量时，每一行都把整张向量表扫一遍。

**改法**（`internal/postgres/retrieval.go` 的 `recallTx`）：

- 这条语句关掉即时编译。
- 两张表的关联改成按主键查。
- 分两步：先对所有记录匹配、打分、排序、取出要返回的那几十条，再只给这几十条挑片段、取标题和上下文。
- 正文每行只转一次小写；要找的词先整理成一组模式，一次比完。
- 向量按「这条记录自己的」和「它的片段的」分开查，都走主键。

**结果**（线上库，2.7 万条导入消息，同一句问话）：

| | 改之前 | 改之后 |
|---|---|---|
| 不带向量 | 62 秒（关掉即时编译后；开着是 77 秒） | 1.8 秒 |
| 带向量 | 285 秒 | 2.2 秒 |

改之前、改之后的输出在同一个只读事务里逐字节相同（不带向量 2,446 行，带向量 2,450 行）。第 3 批的回忆测试、S10、评测测试全部通过。

**没达到的**：R3 要求 300 毫秒以内，现在是 2 秒左右。剩下的时间花在「每一条记录都要比一遍词」上，要再快就得先用索引筛出候选（R2），同时保证结果不变，这一步没做，记入待办清单。R4（导入不变慢）不涉及，这次没有加索引和迁移。R5（快照耗时）见 PR #161。
