# 第 4 批：评测、花费记录和 ChatGPT 历史导入（契约）

**先读 [并行方案与数据约定](../parallel.md)，再读本页，最后读自己的任务包。** 本页和任务包冲突时以本页为准，并立刻告诉协调者。

## 1 这一批做什么

三件互相独立的事：

- **导入**：把 ChatGPT 的聊天记录搬进来。导入前看得到有多少、是哪段时间的；导入中看得到进度，可以暂停；原话先存好、马上能查，整理成记忆在后台慢慢做。
- **花费记录**：每次调用模型，记下用了哪些记忆、花了多少。这一批只记录和提供读取接口，界面留给观测台。
- **评测**：一套带干扰项的回忆题，量出回忆有多准；用同一个模型比较「全塞进去」「只靠向量」「结构化优先」三种做法的准确率和花费。

**上线后用户能感受到的变化**：能把 ChatGPT 的历史搬进来，并马上问到里面的原话；有一份报告告诉你回忆有多准、每次大约花多少。

## 2 现在的事实

- 归档导入已经有了（`POST /v1/connectors/archive`）：整份文件存成一份附件资料，后台解析成一条条消息资料，每条带说话时间、角色、所属对话。它认得 ChatGPT 导出的 `conversations` 结构，也认得 zip。上限是上传 20 MB、解压后 64 MB、10000 条记录。
- 导入之前看不到会导入多少；导入之后只有一句「正在后台解析」，没有进度，不能暂停。
- 旧聊天里的计划不会变成今天的待办（PR #49），这一条已经成立。
- 每天花了多少只有一个合计（`agent_runs` 和 `background_usage` 里的预留花费）；哪次调用用了哪些记忆，没有记录。
- 没有任何评测。

## 3 规则

### 导入（I）

**R1 先预览，不落库。** `POST /v1/connectors/archive/preview`（上传文件）只读不写，返回：

```json
{ "name": "chatgpt-export.zip", "conversations": 812, "messages": 23110, "fromUser": 11480,
  "earliest": "2023-02-11T08:02:00Z", "latest": "2026-09-30T12:40:00Z",
  "alreadyImported": 0, "leftOut": 0, "gaps": [] }
```

`alreadyImported` 是这份文件里已经在库里的消息数；`leftOut` 是因为超过条数上限而不会导入的消息数。

**R2 能吃下真实的导出文件。** 上传上限 200 MB。zip 里只读 `conversations.json`（以及现有支持的文本格式），图片、音频等其他文件跳过并在 `gaps` 里说明。`conversations.json` 解压后上限 512 MB，用流式方式解析，不把整个文件在内存里展开成对象再处理。消息条数上限 200000：超过时导入最新的 200000 条，其余计入 `leftOut`，不拒绝整份文件。

**R3 导入是一个看得见的批次。** `POST /v1/connectors/archive` 照旧保存原始归档，同时建一个导入批次（`import_batches`，状态 `importing`），返回批次 id。后台分小批把消息存成原话，从最新的对话开始，每存完一小批更新 `stored`。全部存完状态变 `done`。

**R4 进度。** `GET /v1/connectors/imports` 返回所有批次：id、名字、状态、`total`、`stored`、`organized`（其中已经处理过抽取的条数）、时间范围、出错原因。

**R5 暂停和继续。** `POST /v1/connectors/imports/{id}/pause`、`.../resume`。暂停后：存原话在当前这一小批存完后停下；这个批次的抽取任务不再被领取（第 2 批 R14）；别的资料不受影响。继续后从停下的地方接着做，不重复存。

**R6 重复导入不重复存。** 同一份文件再导一次，不新增任何资料。新一点的导出里包含旧对话和新对话时，只新增没见过的消息。

**R7 存完就能查。** 一条消息存成原话之后，不等抽取，秘书和副手就能通过第 1 批的原话直达找到它，摘录带着它当时的说话时间和说话人。

**R8 旧话的性质。** 导入的消息保留各自的说话时间；不建今天的待办，不唤醒想法；抽出的记忆一律「待确认」（第 2 批 R7）；AI、系统、工具角色的消息不调模型抽取（第 2 批 R10）。ChatGPT 里被放弃的分支照现有的办法标成历史分支。

**R9 中断不丢不重。** 后台进程在导入中途被杀掉、重启后，接着做完；最后 `stored` 等于 `total`，没有重复的资料。

**R10 出错说清楚。** 不是 zip 也不是认得的格式、zip 里没有对话、文件被截断、超过上传上限，各有各的错误类型和一句人话；这几种情况什么都不存。导入中途失败时状态变 `failed` 并写明原因，已存的保留，继续（`resume`）可以接着做。

**R11 删除。** 删除一次导入（删归档并勾选同时删除它的消息）之后，它的消息、从这些消息抽出的记忆、批次记录都没有了，秘书不再收到。

### 花费记录（L）

**R12 记什么。** 秘书一轮对话、旧的导办台问答、副手运行、抽取，每次模型调用**成功返回**后记一行（S0 已经放好了调用点）：用途、副手、模型名、输入输出 token、花费、对应的对话轮 / 运行 / 后台任务、交给模型的记忆和原话的引用。失败的调用不记；同一个请求重放不记第二行。向量调用这一批不记。

两点说明（2026-10-02 补充）：

- **「成功返回」指模型给回了内容**，不管这段内容后来能不能用。模型返回了、但输出格式不合格或没通过后面的校验，这次调用照样花了钱，照样记一行。调用本身出错、没有拿到任何返回的，不记。
- **「重放不记第二行」只对有重放保护的入口成立**：秘书的一轮对话（同一个请求 id 再发一次不会再调模型）和副手运行。旧的导办台问答接口没有请求 id，同样的请求再发一次就是又调了一次模型，所以每次都记一行；这一批不给它加重放保护。

「模型返回了但内容不合格」这条路现在还走不到 `recordUsageTx`，需要调用点所在文件的写入者补上：抽取在 `processing.go`（第 2 批的 E1），秘书、旧问答、副手在 `desk_turn.go`、`desk.go`、`runs.go`（第 3 批的 Q2）。L 不改这些文件。

**R13 表里不放正文。** `model_usage` 里只有 id、版本、类型、数字，没有任何原话或记忆的文字。

**R14 怎么读。**

- `GET /v1/workspace/usage?from=&to=`：按用户时区的自然日、按用途汇总：调用次数、输入输出 token、花费。
- `GET /v1/workspace/usage/calls?limit=&before=`：最近的调用，一条一行；每条的引用在读取时现查当前文字，取前 80 个字符；已经删除的显示为已删除，不带文字。
- 只有用户本人能读。

**R15 记录不因撤销和删除而消失。** 撤销动作、清空某一轮对话、删除记忆，都不删花费记录：钱确实花了。它们本来就不含正文。

### 评测（V）

**R16 评测集。** 全部是合成数据，放在 `testdata/phase2/eval/`：大约 12 个场景，每个场景 6–12 份资料、2–3 个问法，再混入一批不相干的资料。场景要覆盖这些干扰：同名的两个人；别人的计划；后来取消了；后来做完了；年份容易记错；很晚才导入的旧话；地名相近；同一件事说了两遍、细节不同。每个问法标注：必须交给模型的资料或记忆（标准证据）、不该排在它们前面的干扰项、正确答案里必须出现的事实。

**R17 检索评测（进 CI）。** 每个问法走真实的秘书入口，模型是假的，只抓它收到的内容。指标：标准证据有多少交到了模型手里（召回率）；干扰项排在标准证据之前的比例。结构化数据由评测集自带的「标准抽取结果」按数据约定写入，所以这个指标量的是检索，不是抽取。测试里有一条线：召回率不得低于评测集里记录的基线。基线第一次由协调者看过结果后定，以后只升不降；要降必须协调者批准并写明原因。

**R18 三种做法的对比（协调者手动跑）。** 一个命令行工具 `cmd/pcas-eval`，对同一套问法用同一个模型跑三种做法：把全部资料塞进去（超出模型上限就截断并记录）；只按向量相似度取前几条（没有配置向量模型时改用关键词，并在报告里写明）；产品现在的做法。每种记：答案里标准事实出现了多少（按字符串和别名匹配，不用模型打分）、输入 token、花费、耗时。输出一份表格和一份 JSON。它只连临时库，模型通道由环境变量给，**不连线上库**。执行者用假模型把工具跑通；用真实模型跑由协调者做。

**R19 抽取评测（同一个工具）。** 用真实模型对评测集的资料跑一遍抽取，和「标准抽取结果」比：人、地点、时间、性质各对了多少。同样只由协调者用真实模型跑。

### 界面（U4）

**R20** 导入 ChatGPT 历史的流程：选文件 → 看到预览（多少段对话、多少条消息、哪段时间、有多少已经导过、有多少放不下）→ 确认 → 看到进度（已经存好多少、已经整理多少）→ 可以暂停和继续。出错时说人话。

## 6 接口形状、错误类型和测试入口（2026-10-02 补充，冻结）

### 导入

- `POST /v1/connectors/archive` 的返回在现有字段之外加 `"batchId"`。
- `GET /v1/connectors/imports`：`{ "items": [ … ] }`，新的在前，不分页。每一项：

```json
{ "id": "…", "archiveId": "…", "archiveVersion": 1, "name": "chatgpt-export.zip", "state": "importing", "total": 23110, "stored": 4000, "organized": 120,
  "leftOut": 0, "earliest": "2023-02-11T08:02:00Z", "latest": "2026-09-30T12:40:00Z",
  "errorCode": "", "error": "", "createdAt": "…", "updatedAt": "…" }
```

- `POST /v1/connectors/imports/{id}/pause`、`/resume`：返回上面这样的一项。批次不存在返回 404；状态不允许（例如对已经做完的批次暂停、对正在进行的批次继续）返回 409，错误类型 `import_not_active`。
- 错误类型（预览和导入相同，沿用现有的名字）：

| 情况 | 错误类型 | HTTP |
|---|---|---|
| 扩展名是 zip 但不是 zip；既不是 zip 也不是认得的格式 | `invalid_zip`；`unsupported_archive` | 400 |
| zip 里没有任何对话 | `no_supported_records` | 400 |
| JSON 被截断或不合法 | `invalid_json` | 400 |
| 超过上传上限或解压上限 | `archive_too_large` | 413 |

出错时的返回沿用现有接口的写法，再加一个 `message`：

```json
{ "error": "invalid_zip", "message": "这个文件打不开，它可能不是 zip，或者下载时损坏了。" }
```

`error` 是错误类型，`message` 是给用户看的那句话，各种错误的 `message` 互不相同。T4 断言 `error` 的值，以及 `message` 非空且各不相同，不断言具体措辞。

**删除一次导入（R11、I10）不新增接口**：用现有的 `POST /v1/memory/delete`，目标是这次导入的原始归档资料，即 `{ "id": <archiveId>, "version": <archiveVersion>, "kind": "source" }`，`include_sources` 为真。现有的删除闭包会顺着归档找到它的全部消息和从消息抽出的记忆；批次记录随归档资料的删除级联消失。

- 上限和小批大小做成包级变量，测试里可以调小、用完改回去：

| 变量 | 默认 | 含义 |
|---|---|---|
| `connectors.MaxUploadBytes` | 200 MB | 上传文件的上限 |
| `connectors.MaxArchiveBytes` | 512 MB | 解压后 `conversations.json` 的上限（现有常量改成变量） |
| `connectors.MaxArchiveRecords` | 200000 | 消息条数上限，超过取最新的（现有常量改成变量） |
| `postgres.ImportChunkSize` | 500 | 每一小批存多少条消息；每一小批是一个独立的事务，小批之间检查是否被暂停、是否被取消 |

- 后台进程启动时读环境变量 `PCAS_IMPORT_CHUNK_SIZE`（正整数）覆盖 `ImportChunkSize`。浏览器用例 W4 用它把小批调成 1，配一份两千条消息的合成导出，这样有足够的时间点暂停。不加任何人为的延时。
- 存原话沿用现有的 `source.parse` 后台任务。I9 的「被杀」：测试在 `stored` 增长到一半时取消这次处理，再让租约过期、重新领取。

### 花费记录

- `GET /v1/workspace/usage?from=YYYY-MM-DD&to=YYYY-MM-DD`：日期是用户时区的自然日，两端都包含；不给时默认最近 30 天。只返回有数据的日子，从早到晚：

```json
{ "days": [ { "date": "2026-10-02", "purposes": [
  { "purpose": "secretary", "calls": 12, "inputTokens": 48211, "outputTokens": 3190, "cost": 0 } ] } ] }
```

- `GET /v1/workspace/usage/calls?limit=&before=`：新的在前；`limit` 默认 50、最大 100；`before` 用上一页返回的 `next`：

```json
{ "items": [ { "id": "…", "at": "…", "purpose": "secretary", "agentId": "chatgpt", "model": "…",
    "inputTokens": 4021, "outputTokens": 233, "cost": 0, "turnId": "…", "runId": null, "jobId": null,
    "refs": [ { "id": "…", "version": 1, "kind": "claim", "text": "下周去成都", "deleted": false } ] } ],
  "next": "…" }
```

已删除的引用 `deleted` 为真、`text` 为空字符串。

## 7 第二轮补充（2026-10-02）

- **什么时候记花费。** 模型一返回内容就记，用一个独立的短事务，不和后面的提交放在一起：后面的提交失败、被取消、被回滚，这一行都留着。（R12 原来写的是「在提交结果的那个事务里」，以这一条为准。）
- **L8 里副手的样例。** 副手的输出是自由文本，没有「格式不合格」这回事。副手这一处用这个情形：模型正在生成时，它用到的一条记忆被纠正；模型返回后这次运行被判为失败（「生成期间记忆或授权已变化」），结果没有被采用。预期：仍然多一行花费记录，数字是模型返回的。
- **原始归档的大小。** 保存原始归档用的存储函数（`internal/blob/files.go`）现在写死 20 MB。批准任务 I 改这个文件，范围只有一处：让保存原始归档时可以用 `connectors.MaxUploadBytes` 作为上限；普通附件仍然是 20 MB，一个字节都不放宽。
- **被用户禁止重新导入的消息。** 用户以前删过某条消息并选了「以后不要再导入」，再导入包含它的文件时：这条消息跳过，不算出错，批次照常做完。它既不计入 `total` 也不计入 `stored`（`total` 的意思是「这次要存的条数」），所以做完时两者仍然相等。预览里多一个字段 `blocked`（这样的消息有几条），它不算在 `alreadyImported` 和 `leftOut` 里；`gaps` 里用一句话说明。界面上「这次会导入多少」是 `messages − alreadyImported − leftOut − blocked`。已有测试 `TestArchiveDeletionErasesOriginalCopies` 的预期不变。
- **批次里的 `error`** 是给用户看的那句话，可以直接显示；`errorCode` 是错误类型。

## 8 第三轮补充（2026-10-02）

**预览里几个数怎么分**（任务 I 的问题）。按这个顺序算，四类互不重叠：

1. 文件里一共 `messages` 条。超过条数上限时，只保留最新的那些，其余全部计入 `leftOut`，不管它们以前导没导过。
2. 保留下来的里面：已经在库里的计入 `alreadyImported`；被用户禁止重新导入的计入 `blocked`；剩下的是这次真正要新存的。
3. 批次的 `total` 是「保留下来的 − `blocked`」。已经在库里的消息算作已经存好，直接计入 `stored`，所以做完时 `stored` 等于 `total`。

所以恒有 `messages = leftOut + alreadyImported + blocked + 新存的`。界面上图例不为 `blocked` 单列一行，由 `gaps` 里那句话说明，保持现状。

## 11 补充规则：导入时可以只存原话、以后再整理（2026-10-03）

用户要马上导入，又不想同样的内容调两遍模型（先逐条整理一遍，等整段整理做好再来一遍）。所以导入时可以先只存原话：零模型用量，存好就能问到；整理留到以后。

**R21 先存着、以后再整理。**

- `POST /v1/connectors/archive` 多一个表单字段 `organize`，取值 `later` 或 `now`，不给时按 `later`。
- `later`：这一批的消息照常存成原话，照常分段、分词、建向量（这样才查得到）；**抽取任务不被领取**，所以不调用模型整理。全部存完后批次是「已存好，还没开始整理」。
- `POST /v1/connectors/imports/{id}/organize`：开始整理。之后它的抽取任务照常按优先级 10 被领取。
- 批次列表的每一项多一个字段 `"organizeLater": true|false`。
- 暂停、继续、删除照常可用，和这个选项互不影响。

数据上的做法：`import_batches` 加一列 `hold_organizing boolean NOT NULL DEFAULT false`（**迁移 029，分配给任务 I**）。领取后台任务时，除了跳过已暂停批次的任务，也跳过 `hold_organizing` 为真的批次的抽取任务（分段、分词、向量不跳过）。领取任务的查询在 `jobs.go`，批准任务 I 改这一个条件。

## 12 补充批 4b：导入的聊天记录按整段对话整理（2026-10-03）

第 4 批上线后接着做，单独验收、单独上线。集成分支 `phase2/batch4b`。任务包：[E4](E4-conversation-extraction.md)。它上线之后，用户对「先存着」的那些批次点一次「开始整理」，模型只跑这一遍。

**R24 单位是一段对话。** 上传归档导入的聊天记录，按对话整理：同一段对话里当前分支上的消息按时间顺序交给模型。超过 12000 个字符时在消息边界上切段，后一段开头带前一段末尾的两条消息当上文。

**R26 以整段对话的结论为准。** 后来改了主意的，以最后的说法为准，被放弃的想法不记。用户用「好」「就这个」同意 AI 的方案时，把同意的内容记成记忆，依据是用户那句同意的话，状态是「待确认」。

**R28 替换逐条整理留下的。** 整理一段对话时，这段对话的消息上已有的、系统写的、用户没确认也没改过的记忆先去掉再写新的；去掉时用到它们的旧回答只标「依据已更新」。用户确认过或改过的记忆不动。重复执行不产生重复的记忆。

**R29 进度、队列、花费。** 这段对话的每条消息处理完都写处理记录（`extractor` 为 3），批次的「已整理」按消息数增长。任务走后台队列，优先级 10；批次暂停或「先不整理」时不领取；可以中断后接着做。一次模型调用记一行花费。对秘书说的话、速记、单个文件的整理方式不变。

### 12.1 切段和跨段的补充约定（2026-10-03，答 E4 的四个问题）

**R24a 长度怎么算。**

- AI 说的消息只是上下文，每条最多交给模型前 1200 个字符（和 R23 一致）；用户说的消息完整交给模型。12000 个字符按交给模型的文字算。
- 12000 只算这一段自己的消息，不含开头带的那两条上文。带的两条上文各自最多 1200 个字符，在请求里标明是上文；它们不能当这一段的依据（它们在上一段里已经当过正文）。
- 单独一条用户消息就超过 12000 个字符：这条消息自己成一段，只把前 12000 个字符交给模型，引用必须落在交出去的这部分里。存着的原话不动。这条消息照常写处理记录。

**R25a 指明依据用 `message_index`。** 按整段对话当前分支上的消息从 1 开始编号，全段统一编号，切段后不重新编号；带的上文也用它原来的编号。模型输出的每条记忆带 `message_index` 和逐字引用。

**R26a 改主意跨了段。** 也要以最后的说法为准。做法：

- 从第二段开始，请求里多带一份「前面几段已经记下的」清单 `earlier_memories`：每项是编号 `ref`（这次整理里从 1 起）和那条记忆的陈述。清单只含这一次整理本段对话时写下的记忆，不含用户确认过或改过的。
- 模型的输出多一个可选数组 `withdraw`，里面是要撤掉的 `ref`。被撤的记忆按 R28 去掉旧记忆的同一条路去掉（用到它的旧回答只标「依据已更新」）。不认识的 `ref` 忽略，不算出错。
- 不增加「谁替代谁」的关系，被撤掉的就是不记。
