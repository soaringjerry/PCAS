# Q4 后台进程回收与索引持续推进

2026-10-03 用户要求火速修复服务器间歇性卡死及导入索引长时间不动。

## 规则与操作序列

| 操作 | 预期 |
|---|---|
| CLI 包装进程启动真实服务、服务另起子进程 → 关闭 | 整个专用进程组退出；关闭 RPC 管道，等待包装进程回收 |
| 只杀包装进程 → 再关闭适配器 | 残留服务和子进程也退出；reader 不再持有管道等待 |
| 连续二十次订阅调用并重读登录状态 | 每次完成后没有存活的旧进程；仍保留正常订阅生成与登录隔离 |
| 模型等待 → 取消调用 | 中断、释放整个进程组，回收包装进程 |
| 重复关闭、之后重新启动 | 关闭幂等；关闭的连接不再接受写入，新连接正常初始化 |
| 记忆提取调用较慢，索引任务已排队 | 独立索引通道继续搜索和向量任务，不等待 AI 返回 |
| 暂停导入 → 恢复 | 两个通道都遵守暂停；恢复后继续原有任务和进度 |
| 两个通道领取同一候选任务 | 原租约及 SKIP LOCKED 规则保证不重复持有；停机后仍可回收租约 |
| 大量旧入口在索引前排队 | 独立部分索引及每页五百候选，不能扫描所有提取入口寻找索引任务 |

后台保持一个通用处理通道（含 AI 提取），另加一个只处理搜索与向量的通道；没有增加 AI 模型并发。原每日预算、有限重试、先存着和删除规则继续生效。迁移 033 只添加索引，不重置原文或提取账本。并行处理时页面优先显示正在提取记忆，各索引计数仍真实更新。

worker 限制为 1 GiB 内存、128 个进程/线程、2 个 CPU，防止异常再次拖垮整机。已有失联进程已临时清理；上线验收检查真实整理、搜索、向量计数同时增长，以及多次调用后残留进程为零。

验证使用生成固定 RPC 响应的多级进程树、阻塞提取的双通道测试、隔离 PostgreSQL 的领取/暂停/续跑及完整原有对话回归。部署保留旧镜像、原配置、数据库及文件快照；不涉及未提交的 P1 检索实现。

首轮上线后，已整理从 1,607 增至 1,762，搜索/向量索引从 1,508 增至 1,849/1,848；五轮真实提取后失联服务与僵尸进程均为零，worker 无 OOM 或重启，宿主可用内存约 5 GB。手机和桌面设置页五项进度及当前活动均正常。
