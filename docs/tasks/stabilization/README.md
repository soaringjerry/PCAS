# 稳定化（第 1 阶段之后、第 2 阶段之前）

**目标**：在继续加新功能之前，把第 1 阶段做出来的功能打稳，不再出现"修一个冒一个"。

2026-10-01 的模型分工、文件归属、当前基线与分批派工见 [执行分工](dispatch.md)。协调者只做任务、契约、审查与验收安排，产品实现和测试交给执行者。

**原因**：上线后先后暴露了 Codex 通道不出 JSON、时区写死、报错看不出原因、连续撤销失败等问题，详见 [上线后问题复盘](../../evaluations/2026-10-01-phase1-postlaunch.md)。这些问题都属于同一个模式：契约和测试共用一个盲区，验收又只在实验室环境里做。

**做法**：遵守 [任务流程规则](../process.md)。先由协调者推演状态（本文第 2 节）；再由**不写实现的执行者**按序列表写测试，找出问题；修复之后，在线上用真实配置完整实测；最后用户实际使用一天。

## 1 范围与顺序

| 步骤 | 内容 | 执行者 | 依赖 |
|---|---|---|---|
| 0 | F6 时区、F7 连续撤销（见 [上线后修复](../phase1/postlaunch.md)） | 6.1 Sol × 2 | — |
| T1 | 撤销与动作序列测试（第 2.1 节），含随机序列测试 | 6.1 Sol（不写实现） | F7 合并 |
| T2 | 提醒与时间测试（第 2.2 节） | 6.1 Sol（不写实现） | F6 合并 |
| T3 | 秘书、Telegram、删除传播测试（第 2.3 至 2.5 节） | 6.1 Sol（不写实现） | 0 合并 |
| 修复 | 按 T1–T3 的发现清单分派 | 协调者分派 | T 的 PR 合并 |
| 实测 | [线上实测清单](../phase1/postlaunch.md#线上实测清单) 11 项 | 协调者 | 修复全部部署 |
| 试用 | 用户实际使用一天 | 用户 | 实测通过 |

T1–T3 可以并行。

**测试执行者的规则**：
- 只看契约和本文的序列表，不改产品代码；
- 每条序列写成一个测试，测试名带编号（例如 `TestU3_SkipOrderUndo`）；
- 没通过的用 `t.Skip("finding U3: …")` 标出，写进 PR 描述里的发现清单，写清现象和预期；
- 测试执行者觉得预期本身不合理的，也写进清单，由协调者裁定。

**进入第 2 阶段的条件**：
1. 第 2 节的所有序列都有测试，而且全部通过，没有 skip；
2. 线上实测 11/11 通过；
3. 用户试用一天，没有发现阻碍使用的问题。

## 2 状态推演（序列表）

「预期」一列是要求的行为。标了 **新规则** 的，是这次推演新定下的规则，原来的实现可能还没做到。

### 2.1 撤销与动作（T1）

| # | 序列 | 预期 |
|---|---|---|
| U1 | 秘书新建 → 撤销 | 事项消失；它的提醒、通知一并删除 |
| U2 | 新建 → 修改 → 撤销修改 → 撤销新建 | 两次撤销都成功，事项消失（F7） |
| U3 | 新建 → 修改 → 直接撤销新建（跳过修改） | `newer_action`：「后面还有改动，请先撤销它」；撤销修改后可再撤销新建（2026-10-01 用户确认） |
| U4 | 新建 → 用户手动改了标题 → 撤销新建 | 正常界面产生后续动作记录时为 `newer_action`；未记录的外部改动为 `changed_since`（2026-10-01 用户确认，按记录区分） |
| U5 | 同一件事改两次 A、B → 撤销 A | `newer_action`；先撤销 B，再撤销 A 均成功 |
| U6 | 打勾完成 → 撤销 | 恢复为 todo；还没到点的提醒仍然有效 |
| U7 | 新建（带提醒）→ 提醒已发出 → 撤销新建 | 事项和通知记录都删除；已经发出去的推送和 Telegram 消息无法收回，这是可以接受的 |
| U8 | 副手结果自动采纳 → 撤销 → 放回去 → 撤销 | 每一步都成功；训练样本最后为 0 条 |
| U9 | 自动采纳 → 用户勾掉其中一个子任务 → 撤销采纳 | `changed_since` |
| U10 | 秘书一轮对同一件事做了两个动作（新建 + 加步骤）→ 先撤销新建 | 新建后能在本轮引用新事项；先撤销新建得到 `newer_action`，先撤销加步骤、再撤销新建均成功（2026-10-01 用户确认） |
| U11 | 撤销后用同一个 requestId 重放 | 返回同样的结果，不重复执行；换一个 requestId 再撤销，返回 `already_undone` |
| U12 | 删除某条记忆或来源，它影响到了某个动作涉及的事项 → 撤销这个动作 | 快照已作废，返回 `expired`：「超过 30 天或相关资料已删除，无法撤销」（F10 已实现） |
| U13 | 30 天前的动作 → 撤销 | 返回 `expired`：「超过 30 天，无法撤销」（**新规则**，同 U12） |
| U14 | 秘书派副手（新建 + 排队）→ 撤销 | 还在排队：事项和副手任务一起删除，预留的费用释放；已经开始执行：`work_started` |
| U15 | 网页里撤销 → 再在 Telegram 里点同一个撤销按钮 | Telegram 提示「已经撤销过了」 |
| U16 | **随机序列**：随机组合 20 个可撤销的操作（新建、修改、完成、加步骤、采纳、文档编辑），然后按逆序逐个撤销 | 每一步撤销都成功；最后的事项、文档、副手任务、训练样本，和开始时逐字段一致（簿记字段除外）。用固定种子跑 50 组，失败时输出种子 |

### 2.2 提醒与时间（T2）

| # | 序列 | 预期 |
|---|---|---|
| R1 | 「5 分钟后提醒我喝水」（默认提前 30 分钟，算出的提醒时间已经过去） | **新规则**：提前量算出来已经过去、但截止时间还没到时，到截止时间再提醒；截止时间也过去了，就不设提醒，回执里写明「时间已过，没有设提醒」 |
| R2 | 只有日期的截止时间、当天 09:00 之后才创建 | 同 R1：当天 09:00 已经过去，就在截止当天的 23:59 提醒 |
| R3 | 改截止时间 / 去掉截止时间 | 按原来的提前量重算提醒 / 删除提醒 |
| R4 | 到点之前打勾完成 → 到点 | 不发送 |
| R5 | 完成之后过了提醒时间 → 撤销完成 | **新规则**：提醒时间已经过去超过 1 小时的，不再补发；首页「在等你」照常显示这件事 |
| R6 | 夏令时：墨尔本 2026-10-04 02:00 跳到 03:00，「周日 2:30」这个时间不存在 | 顺延到 03:30，回执里显示 03:30 |
| R7 | 跨夏令时的提醒（周六设、周一到点） | 按当地时间准时触发 |
| R8 | 修改工作区时区 | 已有事项的绝对时间不变；之后的新事项按新时区换算；首页和回执都按新时区显示（F6） |
| R9 | 服务重启前后各跑一次提醒检查 | 不重复生成通知，不重复发送 |
| R10 | Telegram 发送一直失败 | 重试 5 次后停止；首页「到点了」照常显示；日志里有通道名和错误类型 |
| R11 | 推送订阅失效（410） | 删除这个订阅，其他通道照常发送 |

### 2.3 秘书（T3）

| # | 序列 | 预期 |
|---|---|---|
| S1 | 同一段对话里快速发两句：「明天三点开会」，在第一句还没回来时又发「改到四点」 | **新规则**：服务端对同一个 conversationId 的轮次串行处理，第二句能看到第一句建出的事项（R1），改的是同一件事，不会重复新建 |
| S2 | 在首页说「把这个标成完成」（没有 THIS） | 追问是哪件事，或者跳过并说明原因；不能随便改一件事 |
| S3 | 模型返回了合法 JSON，但引用了不存在的别名或 UUID | 跳过这个动作，并说明原因；其他动作照常执行 |
| S4 | 同一句话，换一个 requestId 再发一次 | 建出两件事（这是用户的意图）；同一个 requestId 重发，不重复执行 |
| S5 | 模型同时返回 ask 和 actions | 动作照常执行，同时显示追问 |
| S6 | 点追问的选项 | 作为下一句发送，并引用上一轮的对象 |
| S7 | 在事项页说「做完了」 | 只把当前这件事标为完成 |
| S8 | 超出预算 / 模型超时 / 模型 500 / 返回纯文本 | 分别显示对应的文案和日志阶段；原话都保存了（F4） |
| S9 | 回复超过 2000 字 | 截断，并提示「回答太长，已截断」；不影响动作执行 |

| # | 序列 | 预期 |
|---|---|---|
| T1 | 同一条 update 投递两次 | 只执行一次 |
| T2 | 换成另一个 bot 的 token | 处理进度和当前对话都重置，不会漏掉新 bot 的消息（代码里已有重置，需要测试覆盖） |

## 3 新规则汇总（协调者已定，写入契约）

- **撤销错误码细分**：`changed_since`（没有后续动作记录的业务内容变化）、`newer_action`（同一对象后面还有未撤销的动作，不区分操作者）、`expired`（超过 30 天或相关资料已删除）。见 U3、U4、U5、U12、U13。
- **同轮新建后继续操作**：用户已确认 U10；内部引用协议经协调者审查写入正式契约，F14 实现，T4 独立验证。
- **提醒时间已经过去**的处理：见 R1、R2、R5。
- **夏令时不存在的本地时间**顺延：见 R6。
- **秘书同一对话串行处理**：见 S1。
- **回复过长截断**：见 S9、T4。

这些新规则由修复步骤实现，测试执行者按本文的预期来写测试。
