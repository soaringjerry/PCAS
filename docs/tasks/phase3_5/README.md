## 0 为什么有这一期

第 3 阶段上线后用户指出两处：你说过的事不会自动进首页的事件线；项目和想法不会自动产生。查下来不是坏了，是三条旧规则叠在一起：第 1 阶段定的「自动采纳」开关默认关、只认待办；第 1 阶段写进秘书提示词的「只有用户明确新建项目才能建」；2.6 抽出的期限表只在资料库「眼下」里，没接到首页。2.5 定的那把尺——直接说的可用，转述和带保留的标明，拿不准的留着——只落到了记忆上，没有同样用到待办、想法和项目上。这一期把它用上。

## 1 工作方式

- 契约没写到的实现细节你自己定，写进 PR 描述，不用停下来问。只有三种情况问协调者：要改用户看得见的行为而本页没写；要改第 3 节的接口；本页两条规则矛盾。
- 集成分支 `phase3_5/main`，从 `main` 建。每个窗口一个长分支，PR 的 base 都是 `phase3_5/main`，做完一块就交。
- 不改别的窗口归属的文件。测试和示例只用虚构内容；不读线上数据库；不部署；不碰 `pcas-db-1` 和线上容器；测试库用自己起的一次性容器，`docker run --rm`，用完删掉。
- 改了给模型的资料或输出格式，上线前用真实通道（自己的登录目录）跑一次看原始输出，贴进 PR。
- 2.6 的通用规则 G1–G7（[2.6 契约第 4 节](../phase2_6/README.md#4-各批的规则)）全部适用：上限要有依据和去向、失败不覆盖、模型结果不白花、一处变动不整份重做、判断交给模型程序只校验、读的路径不写、每个后台阶段有自己的预算。

## 2 定下的事

用户 2026-10-08 同意：

1. **没有「自动采纳」开关。** 后台抽出的待办、想法按可信度直接建或留作候选，和记忆同一把尺。设置里那个开关去掉；它原来的值不再有意义。
2. **项目可以自动产生**，先做后报、附撤销，两个触发点（第 4 节 C）。
3. **期限表进首页。** 首页「今天 / 近几天」显示期限表里的预约、截止、固定安排，和待办一起按时间排。
4. **没时间的待办进「在推进」**（待办 13 到此为止）。
5. 从历史导入里来的旧话仍然不建当前待办（PR #49 的规则不变）。
6. 第 2 阶段以来的决定继续有效：团队默认共用全部记忆；不做任何形式的授权门；验收走真实的路。

## 3 批次之间的接口

后端提供、界面使用。HTTP 路径和字段由后端定，写进骨架 PR 的描述（开工一小时内先交骨架）。

| 读什么 / 做什么 | 要求 |
|---|---|
| 日程（首页用） | 给一个日期范围，返回这段时间里每一天的条目：期限表的截止、预约、固定安排的**展开后的发生日**（周期性的按周期展开到范围内），加上有截止或安排时间的待办；每条带来源（期限表行指向记忆、待办指向事项）、类型、时间（没说清时间的只有日期并标明）。范围上限和依据写进 PR |
| 自动建出来的事项 | 现有的工作区快照里，事项多一个来源标记：谁建的（秘书 / 后台抽取 / 后台主题积累）、依据的原话或记忆；建的动作在现有的操作记录里，能撤销 |
| 候选 | 现有的候选接口不变；留作候选的理由（转述 / 带保留 / AI 建议 / 拿不准）写在候选上 |
| 设置 | `autoAccept` 字段读的时候仍返回（界面切换完再删），写入忽略 |

## 4 各批的规则

### A 期限进首页

- **A1** 首页「今天」那条线和「近几天」用第 3 节的日程接口：当天的预约和截止排进时间线，固定安排按当天的发生时间排，和有时间的待办混排；三天内的截止进「近几天」（沿用现有三天）。
- **A2** 期限表里「日期没说清」的条目不上时间线，放在「近几天」末尾一组，带原话。（2026-10-08 作废：没有确定时间的不上首页，见[第 3.6 阶段](../phase3_6/README.md)。）
- **A3** 已过期不知是否完成的截止，按现有「已过截止」的样式显示，点开能说「做完了」——这会落到底下那条记忆上（标完成），不是新建待办。
- **A4** 周期性安排的展开由程序做；展开范围和依据写进 PR（预期：范围就是请求的日期范围，不预先物化）。

### B 待办和想法按可信度直接建

- **B1** 后台抽取（当面说的话、后台整理的对话、接入的资料）得到的待办和想法：**直接表达、不带限定、不是转述、不是 AI 的建议**的，直接建；其余留作候选并写明理由。「直接表达」「转述」「带保留」由抽取模型判断（现有 `explicit`、`acquisition`、`confidence` 字段），程序只按字段取值，不做关键词判断。置信度门槛沿用现有 0.98 还是改，由你定并写明依据。
- **B2** 历史导入（`imported`、`historical` 分支、非本人角色）不建，沿用现有规则。
- **B3** 建出来的事项带来源标记（第 3 节），在首页「你不在的时候，我做了这些」里有一条回执，附撤销。撤销连带这条事项的来源标记，不删原话。
- **B4** 去重沿用现有候选去重；同一句话重跑不建第二条。
- **B5** 一段对话或一份资料一次抽出的待办超过上限时，超出的留作候选并记数（G1）；上限和依据写进 PR。
- **B6** 设置里的「自动采纳」去掉；旧值不再读。

### C 项目自动产生

- **C1 秘书听出一件大事。** 秘书的提示词改为：用户说的事如果**有目标，并且有截止或要分好几步做或要做好几天**，而且不属于已有项目，就建项目（`project: new:名称`）并把这句话里的待办归进去；回执写明「建了项目「…」」，附撤销；撤销连带归进去的待办回到无项目。只是一件单步的事不建项目。是否是大事由模型判断，提示词里写清三个条件；程序只校验名称非空、不与已有项目同名（同名归入已有）。
- **C2 后台主题积累。** 2.5 的主题分组里，一个主题名下的当前记忆达到 N 条，其中有目标类（goal）记忆且有期限表行时，建项目并把这个主题分组连到它（和项目分组一样带 `work_item_id`，这样项目交接说明的输入就有了）；回执进「你不在的时候，我做了这些」，附撤销；撤销只断开连接和删除空项目，不动记忆。N 的依据写进 PR（预期在 8–15 之间：少了会把一次聊天建成项目，多了等不到）。每天自动建的项目数有上限，依据和超出去向写进 PR（超出的下一天继续，不丢）。
- **C3** 两条路都要先用模型判断「是不是已有项目的事」，是就归入不新建；判断不靠名字字面相等。
- **C4** 自动建的项目一样进现状块的排班（第 3 阶段 H3）。

### D 没时间的待办

- **D1** 没有截止、没有安排时间、不是「尽快」的待办进首页「在推进」一列，按最近有进展的在前（交互原则「两条推进线」）。
- **D2** 「在推进」显示条数有上限，依据和超出去向写进 PR（预期：显示最近 N 条，其余在项目里）。

### T 独立验收

只读本页写测试，先冻结预期，再看实现。

- **T1** 夹具：2.6 的线上规模夹具加 200 条期限表行（含周期性、没说清日期的、已过期的）、30 条抽取候选（直接表达 / 转述 / 带保留 / AI 建议各若干）、三个主题分组（一个达到 C2 的条件，两个差一项）。
- **T2** 逐条验 A–D 和 G1–G7；重放同一句话不建第二条；撤销序列：建 → 撤 → 再抽到同一句不重建；自动建项目 → 撤销 → 待办回到无项目、记忆不动。
- **T3** 日程接口的周期展开按时区和夏令时验；三天边界验。
- **T4** 耗时：日程接口一个月范围的读在多少毫秒内；每天自动建项目的调用数。
- **T5** 浏览器回放白皮书 §16 第 3.5 行的三个验收场景（虚构数据）。

## 5 验收与上线

1. 各批 PR 合入 `phase3_5/main`，协调者读代码后合并。
2. T 在 `phase3_5/main` 上全部通过。
3. 协调者合入 `main`、备份、上线、线上用默认通道实测：说一句带日期的话看首页；对秘书说一件多步的事看项目；撤销。
4. 上线后核对：首页日程条数和期限表行数对得上；自动建的事项和项目各几条、撤销了几条；候选里剩下的理由分布。
5. 协调者更新白皮书 §15、§16、交互原则、待办 11、13。
