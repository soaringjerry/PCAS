## 1 这一批做什么

把一句问话拆成条件，先按条件在结构化记忆里定位，再用原话补上漏掉的；回答用一张时间轴卡片呈现：哪天说的、想做什么、后来怎样了。

**上线后用户能感受到的变化**：问「我去年说去成都要干什么来着」，秘书立刻答出来，下面一张时间轴，每条都能点开看当时的原话，做完的、取消的、后来改过的都标着。年份记错了也能找到，并告诉你实际是哪天说的。

## 2 和第 2 批的关系

这一批用的是第 2 批写出来的数据：记忆上的人和地点（`claim_mentions`）、什么时候说的（`expressed_at`）、说的是什么时候的事（`event_from`、`event_to`）。**你不用等第 2 批的抽取做完**：这些表在 S0 合入后就有了，测试里按 [数据约定](../parallel.md) 直接造数据。

## 3 现在的事实

- 检索是关键词加向量相似度。「去年」「成都」只被当成普通的词；按时间只能给一个时点，不能给一段。
- 秘书拿到检索结果后，从全部记忆里按 id 挑出来放进提示词，每条只有文字和可用状态，没有时间、地点、人。
- 时间轴卡片：模型引用了两条以上记忆才出现；日期取的是资料的记录时间；「做完没有」是按同一份资料里的第一个事项猜的。
- 把一段对话转交给副手时，检索只按这次的要求和事项找资料（待办第 24 项）。

## 4 规则

### 拆条件（Q1）

**R1 一个纯函数。** `PlanQuery(text string, now time.Time, loc *time.Location) QueryPlan`，放在 `internal/memory/query_plan.go`。不查库，不调模型，同样的输入永远得到同样的输出。

```go
type QueryPlan struct {
    Time    *PlanTime // 没有时间说法时是 nil
    Natures []string  // 性质提示，可以为空
    Recall  bool      // 这句话是在回忆以前说过的事
}
type PlanTime struct {
    From, To  time.Time // 左闭右开
    Precision string    // day / week / month / year / range
    Axis      string    // said / event / either
    Phrase    string    // 原句里的那个说法
}
```

**R2 认得哪些时间说法。** 按用户时区、以 `now` 为准换算成区间：

| 说法 | 区间 |
|---|---|
| 今天、昨天、前天、明天、后天 | 那一天 |
| 这周、上周、下周（周一为一周的开始）；上周五这类「上周 + 星期几」 | 那一周；那一天 |
| 这个月、上个月、下个月 | 那个月 |
| 今年、去年、前年、明年 | 那一年 |
| 2025 年；2025 年 3 月；3 月 12 日（没写年份取不晚于今天的最近一次）；3 月（同理） | 那一年；那个月；那一天；那个月 |
| 最近、这几天 | 包含今天在内的 30 个日历日；包含今天在内的 7 个日历日。终点是明天零点，起点是终点往前 30（7）天；精度写 `range` |

一句话里有多个时间说法时取第一个。认不出来就是没有，不猜。

**R3 说的时间还是事的时间。** 时间说法后面紧跟着「说、提、聊、讲、问、告诉、记」这类动词（「去年说」「上周提过」）时 `Axis` 是 `said`；其余是 `either`。这一版不产出 `event`，留给以后。

**R4 性质提示和回忆标记。** 句子里有「想、打算、计划、准备、要去、要做、要干」：`intention`、`plan`；「喜欢、爱吃、不吃、讨厌、习惯」：`preference`；「决定、定了」：`decision`。有「说过、提过、来着、之前、上次、记得、当时」之一，`Recall` 为真。

### 按条件找（Q2）

**R5 只对团队的检索生效。** 秘书、副手、手动转交这三个入口（第 1 批的 `Scope.Team`）用规划；对外的 `/v1/memory/recall` 一个字节不变。规划只看用户**这一句**话，不看对话里前面的内容。

**R6 认出问的是谁、哪里。** 这句话里出现了某个有效实体的别名（别名至少 2 个字符，不分大小写），这个实体就是候选。「我」**不算实体条件**：一句话里只有「我」、没有别的认得的名字时，就是没有实体条件。它只影响排序（R7：主体是用户本人的排在前面）。一个也认不出时就没有实体条件。

**R7 第一步：结构化定位。** 有实体条件或时间条件时，先找符合条件的当前有效记忆：

- 实体条件：记忆提到了候选实体之一，或者主体是它；
- 时间条件：`said` 看说话时间落在区间里；`either` 是说话时间落在区间里、或者事件时间和区间有重叠，满足一个即可；
- 两个条件都有时要同时满足。

排序：主体是用户本人的在前；性质和提示一致的在前；其余按说话时间从新到旧。

**R8 时间对不上就放宽。** 有时间条件、有实体条件，同时满足的一条也没有，但只按实体能找到：用只按实体找到的结果，并在给模型的内容里加一行说明「按这个时间没有找到，下面是其他时间说的，回答时说明实际日期」。只有时间条件而没找到时不放宽。

**R9 第二步：原话和原来的检索补漏。** 第一步之后，照现有的办法（关键词、向量、第 1 批的原话摘录）接着找，去掉重复的。原话摘录里，说话时间落在时间条件区间内的排在前面。没有任何条件时，第一步跳过：交给模型的记忆和原话是哪些、按什么顺序，和这一批之前完全一样。每条记忆那一行的文字，在记忆没有时间、地点、人这些新字段时逐字相同；有这些字段时只是在行尾按 R12 追加，前面的部分不变。

**R10 现有的过滤一个不少。** 副手的类别设置、是否包含推测、事项上的排除、项目归属、对这个副手关着的记忆、第 1 批 R2a 的原话收紧，全部照旧生效。结构化定位只决定「先找谁」，不决定「谁能看」。

**R11 预算不变。** 给秘书的记忆最多 20 条、原话最多 6 段共 2400 字符，副手和手动转交照旧。第一步找到的排在前面，超出的丢掉，不报错。

**R12 提示词里带上时间和地点。** 每条记忆那一行，在现有内容之后追加（有才写）：`/ 说于 2025-11-03 / 事件 2025-11 / 老王 / 成都`（先人后地点，各自按名字排序）。日期按用户时区，事件时间按精度写（某天、某月、某年、起止）。库里的区间是左闭右开的，写给人和模型看时用**实际覆盖的最后一天**：区间 `[06-12, 06-15)` 写成「06-12 至 06-14」，不写 06-15。秘书指令里加一句：回忆类的问题按给出的日期回答；看到 R8 那一行说明时，要说出实际是哪天说的。

**R12a 追加的部分不占名额。** 挑哪些记忆、挑到哪一条为止，按**没有追加内容**的那一行来算（秘书的条数上限、副手交接内容的字节上限都是这样）。挑定之后再把时间、地点、人追加上去。这样有没有新字段，交给模型的条目和顺序都一样；交接内容可能因此比原来的上限多出追加的那一点，这是允许的。

**R13 依赖照记。** 实际交给模型的每条记忆和原话照第 1 批 R5 记进依赖。

### 时间轴（K）

**R14 条目内容。** 模型在 `used` 里引用的每条记忆是一个条目：`at` 是说话时间。记忆自己有说话时间就用它；没有时（第 2 批之前的旧记忆都没有）看它出自的那份资料，按第 2 批 R5 同样的办法取：资料有表达时间用表达时间，资料是用户亲手输入的用记录时间；都不满足就留空。**不拿导入时间顶替**：出自没有日期的导入文件的记忆，`at` 就是空的；带上事件时间和提到的人、地点（数据约定第 3.4 节）。按说话时间从早到晚排，没有时间的排在最后。原话条目照旧不进时间轴。

**R15 后来怎样了。** `status`：

- 这条记忆出自秘书的某一轮对话、那一轮建了事项时，看那一轮建的事项（通过那一轮的记录找，不再按「同一份资料里的第一个事项」猜）。「那一轮建了哪些事项」以这一轮保存的创建回执为准（新建待办、想法、项目的回执里有事项 id，长期保留）；动作记录的明细 30 天后会清空，不能只靠它，否则去年的事永远查不到后来怎样了。事项已经不存在的不算：全部做完是 `done`；全部取消或放弃是 `dropped`；其余（还有没做完的，或者有的做完有的取消）是 `open`；
- 没有关联事项、但这条记忆后来被纠正或改过（有「改变」或「纠正」类的新版本）：`changed`，文字用现在的版本；
- 其余是 `open`。

**R16 什么时候出时间轴。** 这句话是回忆类的（R4 的 `Recall`）并且至少引用了一条带说话时间的记忆时，出时间轴，哪怕只有一条。其他情况和现在一样：引用两条以上才出。

### 界面（U3）

**R17** 时间轴每一条显示：哪天说的；说的是哪天的事（有才显示，并且和「哪天说的」能分清；一段日子显示到实际覆盖的最后一天，见 R12）；后来的状态（已完成、已取消、后来改过，没有变化的不标）；提到的人和地点。没有说话时间的显示「时间不详」。点一条能看到当时的原话（已有的行为）。

## 7 验收首轮的裁定（2026-10-02）

- **V1 的日期写法。** 界面把说话的日期写成「2 月 3 日」加一个小字的年份，读出来是「2月3日2025年」。契约 R17 只规定显示哪些内容，没有规定年和日谁在前。断言改成不依赖顺序：时间元素的 `dateTime` 属性是那一刻的时间；可见文字里同时有「2月3日」和「2025年」。
- 首轮里因为造数阶段出错而失败的用例，按你已经修正的夹具重跑，不算发现。
- 第 2 批那两组旧抽取测试的预期由 T2 在它的验收 PR 里改，第 2 批进 main 后这边自然通过；在那之前这两条失败在报告里单列。

## 8 验收第二轮的裁定（2026-10-03）

- **R12 里人和地点的先后。** 契约里那一行只是例子，没有规定顺序。以实现为准并写成规则：先写人，再写地点；各自按名字排序。界面上也是先人后地点。T3 把冻结的后缀改成这个顺序（S6、S8 等用到精确后缀的地方）。
- **S7 里对原话的反面断言。** 类别不给这个副手、是推测而副手不含推测、属于别的项目，这三种限制只管**记忆**，不管原话：按第 1 批 R2，原话不按类别和项目过滤，所以这三个子用例里那句原话可以出现在「相关原话」里，只断言那条记忆没有交给模型。原话跟着收紧的只有两种情况（第 1 批 R2a）：对这个副手关着、在这件事上被排除；这两个子用例照旧断言原话也收不到。
- **V1 里事件日期的年份。** 事件日期和这一条左边「哪天说的」是同一年时，界面不重复写年份（没有说话时间时，和今年相同则不写）。这是允许的。断言改成：月和日一定在；年份只在和左边那个年份不同时才要求出现。
